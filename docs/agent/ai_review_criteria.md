# AIエージェント生成物のレビュー観点

## 概要

Claude が生成した実装コード・単体テスト仕様書・単体テストコードをレビューする際の観点を整理したドキュメント。

**対象読者**: 人間のレビュアー。AIエージェントへのプロンプトには直接組み込まない。

コーディング規約やフレームワーク規約の確認ではなく、**AIに生成を委託することで固有に生じるリスク**に絞って記載する。
一般的なコードレビュー観点は `docs/conventions/coding_rules.md` 等を参照。

### 適用タイミング

| 観点 | 実装コードレビュー時 | テストコードレビュー時 |
|------|:---:|:---:|
| 1. 善意のスコープ逸脱 | ✅ | |
| 2. 曖昧な記述の独自解釈 | ✅ | |
| 3. 文字列・識別子の言い換え | ✅ | |
| 4. 幻覚によるAPI・メソッドの不在 | ✅ | ✅ |
| 5. テストコードが「通るように」作られている | | ✅ |
| 6. テスト仕様書が実装のトレースになっている | | ✅ |
| 7. 複数セッション・分割実装時の不整合 | ✅ | ✅ |

---

## Claude 固有の失敗パターンと確認観点

### 1. 善意のスコープ逸脱

Claude は「設計書に書かれていること」だけでなく「書かれていないが必要そうなこと」も実装しようとする。

**確認内容**

- 変更ファイル一覧（詳細設計書セクション1）に**記載のないファイルを変更していないか**
  - 差分レポートで全ファイルを必ず確認する
- 基本設計書「3.2 対象外」に記載した機能が**混入していないか**
- 既存コードへの「ついでのリファクタリング」が含まれていないか（設計書に記載のない既存関数・クラスへの変更が含まれていれば対象）
- バリデーション・ログ・キャッシュなど「あった方がいい処理」が設計書に**なく追加されていないか**

> **根本対策**：スコープ逸脱が多い場合、基本設計書の「3.2 対象外」の記述が不足しているシグナル。

---

### 2. 曖昧な記述の独自解釈

設計書に書かれていない部分を Claude が自己判断で補完する。設計書が曖昧なほど顕著に現れる。

**確認内容**

- エラー時の挙動（例外を伝播させるかログだけにするか）が設計書の意図と一致しているか
- 設計書に明示のないデフォルト値・フォールバック処理が追加されていないか
- 複数の解釈が可能な仕様を「より良い方」と判断して実装していないか

> **根本対策**：この種の誤りが多い場合、詳細設計書の「処理仕様」における「実装判断ポイント」の記述が不足しているシグナル。

---

### 3. 文字列・識別子の言い換え

Claude は「意味が同じ」と判断すると文言を自然な表現に言い換えてしまう。

**確認内容**

- エラーメッセージ文言が詳細設計書「エラーハンドリング」テーブルの**完成形と一字一句一致**しているか
- 設定キー名（例：`MAIL_TIMEOUT` vs `SMTP_TIMEOUT`）が設計書のスペルと**完全一致**しているか
- ログ出力の文言が設計書の完成形と一致しているか
- 関数名・引数名に微妙なリネーム（例：`fetch_user` → `get_user`、`send_mail` → `send_email`）が発生していないか

---

### 4. 幻覚によるAPI・メソッドの不在

Claude は存在しないメソッド・ライブラリのAPI・キーワード引数を自信を持って使用することがある。実行するまで気づけない。

**確認内容**

- インポートしているモジュール・クラス・メソッドが**実際に存在するか**確認する
- 使用しているキーワード引数がライブラリの公式APIに存在するか確認する（非公式・削除済みのAPIを使っていないか）
- フレームワーク（Invenio3 / Flask）の内部APIを直接呼んでいる場合、そのパスが実際のソースコードに存在するか確認する
- `except Exception: pass` や `except Exception: return None` による**例外の丸ごと握りつぶし**がないか（エラーを隠蔽して実行は通るが問題が検知できなくなる）

> **根本対策**：フレームワーク固有の内部APIを使う箇所には、詳細設計書の「実装上の注意事項」にファイルパス・クラス名を明示しておく。

---

### 5. テストコードが「通るように」作られている

Claude はテストの通過率を上げようとする動機が働き、実質的に何も検証しないテストを生成することがある。

**確認内容**

- **テスト対象そのものをモックしていないか**
  - 例：`EmailService.send_registration_email` をテストするのに `EmailService` ごとモックする
- アサーションが `assert result is not None` だけで終わっていないか
- 異常系・境界値テストが**省略されていないか**（正常系だけ実装されているケース）
- `mock.assert_called_once_with(...)` で「呼ばれたか」だけを確認し「返却値・副作用」を検証していないか
- テスト関数の中身が空（`pass`）または trivially true なアサーションになっていないか

> **根本対策**：基本設計書「完了条件」を外部から観測できる振る舞いで具体化しておく。「〜が呼ばれること」ではなく「〜が返ること」「〜がDBに記録されること」の形式で記載する。

---

### 6. テスト仕様書が実装のトレースになっている

テスト仕様書（What）ではなく、実装フロー（How）をそのまま書き直したものになる。

**確認内容**

- テストケースが「ステップ3で〇〇を呼ぶ」という**内部実装の記述**になっていないか
- 仕様（外から見た振る舞い）ベースで書かれているか
  - ❌ NG：「`MAIL_SERVER` が `None` のとき `return` されること」
  - ✅ OK：「SMTP未設定のとき、メール送信がスキップされ API は正常レスポンスを返すこと」
- 「実装しやすいケース」だけに偏り、複雑な異常系が省かれていないか
- 基本設計書「完了条件」・詳細設計書「エラーハンドリング」の各項目に対応するケースが揃っているか

> **根本対策**：基本設計書「完了条件」・詳細設計書「エラーハンドリング」のケースが不十分だと、テスト仕様書もそのまま薄くなる。仕様書側の各項目を具体化する。

---

### 7. 複数セッション・分割実装時の不整合

設計書を分割して複数セッションに委託した場合、後のセッションが前のセッションの実装を知らないまま実装する。このプロジェクトでは詳細設計書の分割が**標準ワークフロー**のため、分割実装時は毎回確認する。

**確認内容**

- 前のセッションで実装した関数のシグネチャと、今回の呼び出しコードが**一致しているか**
- 前のセッションで定義した定数・設定キーを、今回のセッションが**別名で再定義していないか**
- `import` パスが前のセッションの実際のファイル構成と一致しているか
- `patch` パスが**テスト対象モジュール内でその名前が参照されているパス**になっているか
  - 例：`mail.send` をモックする場合、`flask_mail.Mail.send` ではなく `app.services.email_service.mail.send` のように、テスト対象モジュール内のパスを指定する

## 優先度まとめ

| 優先度 | 観点 | なぜ重要か |
|--------|------|-----------|
| **高** | 変更ファイルの範囲確認（観点1） | 意図しない変更は後から発見が難しく、影響範囲が読めない |
| **高** | テストが実質的に機能しているか（観点5） | 通るだけのテストは存在しないのと同じ。見抜けないまま通過するリスクが高い |
| **高** | 幻覚によるAPI・メソッドの不在（観点4） | 実行時エラーになるが、コードレビューだけでは見落としやすい |
| **中** | 文字列・識別子の完全一致（観点3） | 発生頻度は高いが影響は局所的。実行時エラーやログ不一致として比較的早期に検知できる |
| **中** | 善意の機能追加の混入（観点1・2） | バグの温床・設計書との乖離が広がる |
| **中** | テスト仕様書の仕様ベース記述（観点6） | 仕様ベースでないとリグレッション検知力が下がる |
| **中** | 複数セッション間の不整合（観点7） | このプロジェクトでは分割実装が標準のため毎回確認。importエラー等として実行時に表面化する |

## 設計書フィードバックの観点

レビューで問題が頻出する場合、コードではなく**設計書の品質が原因**であることが多い。
以下の対応を検討し、次案件以降の設計書に反映する。

| レビューで多い問題 | 設計書の改善箇所 |
|-----------------|----------------|
| 設計外の機能が追加される | 基本設計書「3.2 対象外」の充実 |
| 実装の解釈がずれる | 詳細設計書「処理仕様」の実装判断ポイント追加 |
| 文字列・キー名が違う | 詳細設計書「エラーハンドリング」の文言を完成形で記載 |
| テストが弱い・仕様トレース | 基本設計書「完了条件」を振る舞いベースで具体化 |
| 変更範囲が広がる | 詳細設計書「変更ファイル一覧」の網羅性向上 |
| API幻覚が多い | 詳細設計書「実装上の注意事項」にファイルパス・クラス名を明示 |
