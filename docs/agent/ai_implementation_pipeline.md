## 1. 概要

WEKO3の開発プロセスにおいて、実装工程をAIエージェントと人間の協業で効率化するためのパイプライン設計である。

- **バックエンド実装**: 詳細設計書から Python/Flask/Invenio3 の実装コードをエージェントが生成し、人間がレビュー・修正・動作確認を行う
- **フロントエンド実装**: 画面設計書（Excel）から React/AngularJS/jQuery の実装コードをエージェントが生成し、人間がレビュー・修正・動作確認を行う
- **並列実行**: バックエンドとフロントエンドは並列で実行し、両方が完了後に最終確認を行う

エージェントの主担当を「設計書に基づく実装コードの初期生成」に限定し、レビュー、修正、動作確認は人間が行う。

## 2. 前提条件

| 項目 | 内容 |
|------|------|
| 設計書は人間が作成済み | 基本設計書、詳細設計書（バックエンド）、画面設計書（フロントエンド）は人間が設計工程で作成済み |
| 設計書の整合性は担保済み | 詳細設計書と画面設計書のAPI仕様（URLパス、JSON構造）は設計段階で人間が整合性確認済み |
| エージェントは設計書を「実装の仕様」として受け取る | 設計内容の妥当性や見直しは行わず、設計書通りに実装する |
| 開始フェーズは実装コード生成 | ソース分析・実装仕様書生成は行わない。詳細設計書/画面設計書を直接入力として実装コードを生成する |

## 6. エージェント構成

| フェーズ | 担当 | 入力 | 出力 |
|----------|------|------|------|
| ① 実装コード生成 | **Senior Developer** (BE) / **Frontend Developer** (FE) | 設計書 + 規約 + 参照資料 + 既存コード | 実装ファイル一式 |
| 🔴 人間レビュー+修正ループ | 人間 | 実装コード | 承認 or 修正指示 |
| ② コード修正 | 人間 / エージェント（必要時のみ） | レビューコメント + 実装コード | 修正済み実装コード |
| ③ AI支援（必要時） | Backend Architect / Code Reviewer | 失敗ログ、該当コード、設計書 | 原因候補、修正方針 |
| 🔴 人間共同確認 | 人間 | 両方の実装コード + Docker環境 | 結合動作確認結果、完了判断 |

### エージェント選択の理由

- **Senior Developer**: 設計書からPEP8準拠のPython実装コードを生成できる。Black/isort/Flake8の規約を遵守したコード生成が可能
- **Frontend Developer**: 画面設計書からReact/AngularJS/jQueryのフロントエンド実装を生成できる。デザイン規約（Sass変数、コンポーネントパターン）に従ったUI実装が可能
- **Backend Architect**: Invenio3/Flaskのアーキテクチャ理解があるため、AI支援フェーズで原因調査・修正方針の提示が可能
- **Code Reviewer**: 正しさ・保守性・セキュリティ・パフォーマンスに焦点を当てた原因分析が可能
- **Security Engineer**: セキュリティ懸念（入力検証、認証・認可、情報漏洩）の確認が必要な場合にのみ使用

## 7. 各フェーズの詳細

### 7.1 実装コード生成（エージェント）

設計書に基づき、コーディング規約・デザイン規約を参照しながら実装コードを生成する。

#### バックエンド（Senior Developer）

**入力**（配置先は [../../CLAUDE.md](../../CLAUDE.md)「ドキュメントディレクトリ構成」を参照）:

| 入力 | 必須/任意 |
|------|----------|
| 詳細設計書 | 必須 |
| コーディング規約 | 必須 |
| 命名規約 | 必須 |
| フレームワーク参照資料 | 任意 |
| 既存コード | 必須 |
| 案件メモ | 任意 |

**生成対象**:

| 生成対象 | 設計書項目 | 出力例 |
|----------|-----------|--------|
| ビジネスロジック | 処理フロー、関数インターフェース | `weko_deposit/api.py`（関数追加） |
| DBマイグレーション | データ構造変更 | `alembic/versions/xxxxx_*.py` |
| 設定変更 | 設定項目追加・変更 | `docker-compose.yml`, `instance.cfg` |
| ルーティング | APIエンドポイント追加 | `weko_swordv3/views.py` |
| 定数/列挙型 | 状態定義、エラーコード | `weko_deposit/constants.py` |

#### フロントエンド（Frontend Developer）

**入力**（配置先は [../../CLAUDE.md](../../CLAUDE.md)「ドキュメントディレクトリ構成」を参照）:

| 入力 | 必須/任意 |
|------|----------|
| 画面設計書（Excel） | 必須 |
| デザイン規約 | 必須 |
| コンポーネント参照資料 | 任意 |
| 既存コード | 必須 |
| 案件メモ | 任意 |

> **画面設計書の読込方法**: Frontend Developerは **xlsxスキル** を使用してExcelを直接読み込み、シート内の表データ（コンポーネント一覧、レイアウト情報、動作仕様）を取得する。変換工程は不要。

**生成対象**:

| 生成対象 | 設計書項目 | 出力例 |
|----------|-----------|--------|
| コンポーネント | 画面構成、UI要素 | `weko_items_ui/static/js/components/ItemDetail.jsx` |
| テンプレート | 画面レイアウト | `weko_items_ui/templates/weko_items_ui/item_detail.html` |
| スタイル | デザイン仕様 | `weko_items_ui/static/css/weko_items_ui/styles.bundle.scss` |
| 状態管理 | 画面遷移、状態遷移図 | `weko_items_ui/static/js/store/itemActions.js` |

#### 実装時の必須ルール

エージェントは以下のルールを必ず遵守する：

1. **スコープ制約の確認**: 詳細設計書にセクション 0「スコープ制約（今回やらないこと）」が存在する場合、実装着手前に必ずそのセクションを確認し、記載された機能・処理は実装しないこと
2. **設計書厳守**: 設計書の処理フロー・インターフェース・UI仕様を厳密に従う。設計書にない機能は実装しない
3. **規約遵守**: コーディング規約・デザイン規約に従う。違反するコードは生成しない
4. **既存コードとの整合性**: 既存のimportスタイル、クラス設計パターン、CSS変数を使用する
5. **最小変更原則**: 設計書で指定された範囲のみ変更する。設計書の範囲を超えるリファクタリングは行わない
6. **マイグレーションの安全性**: DBマイグレーションはアップ/ダウン両方の定義を含む。データ損失のリスクがないことを確認する

### 7.2 人間レビュー（任意回数）

実装コードに対して人間がレビューを行い、修正指示を出し、エージェントが修正するループを任意回数繰り返す。

> AI固有のリスクに絞ったレビュー観点（スコープ逸脱・識別子の言い換え・API幻覚など）は [ai_review_criteria.md](ai_review_criteria.md) を参照。コーディング規約の観点は `docs/conventions/coding_rules.md` を参照。

#### レビュー確認項目

| 確認項目 | バックエンド | フロントエンド |
|----------|-------------|---------------|
| 設計書整合性 | 詳細設計書の処理フロー、インターフェース、例外処理が正しく実装されていること | 画面設計書のレイアウト、状態遷移、UI動作が正しく実装されていること |
| コーディング/デザイン規約 | PEP8、Black、import順序遵守 | デザインシステム変数の使用、コンポーネント構成遵守 |
| 既存コードとの互換性 | 既存APIのbreaking changeがないこと、import循環がないこと | 既存コンポーネントの再利用、既存CSS変数の使用 |
| DBマイグレーション | アップ/ダウン両方の定義、データ移行ロジックの安全性 | - |
| 設定変更 | 環境変数のデフォルト値、後方互換性 | - |
| エラーハンドリング | 例外の種類・発生条件・ログ出力 | エラー画面・トースト通知 |
| レスポンシブ対応 | - | 複数のビューポートサイズでの表示確認 |

#### レビュー記録表（implementation_review.md）

実装コード生成が完了した後、エージェントは `docs/cases/<案件名>/implementation_review.md` にレビュー記録表の雛形を生成する。
人間はこのファイルにレビュー内容を記入し、レビューループを管理する。

**雛形に含める内容**:

| セクション | 内容 |
|-----------|------|
| ヘッダー | ブランチ名・レビュー実施日・レビュー者の記入欄 |
| レビュー対象ファイル一覧 | 今回の変更ファイルと変更種別 |
| チェックリスト | 設計書整合性・コーディング規約・既存コード互換性・設定変更の各確認項目（`☐ OK / ☐ NG` 形式） |
| レビューコメント欄 | 指摘がある場合の記入欄（`🟡` 形式） |
| 修正対応記録欄 | 修正発生時の記録欄（`🔧` 形式） |
| 最終承認欄 | 承認記録欄（`✅` 形式） |

> **配置先**: `docs/cases/<案件名>/implementation_review.md`（[../../CLAUDE.md](../../CLAUDE.md)「ドキュメントディレクトリ構成」を参照）

#### コメント形式

レビュー記録表の各欄に以下の形式で記入する：

```markdown
## レビューコメント
> 🟡 [レビュー者: 氏名] 指摘内容
> → 修正指示
```

```markdown
## 修正対応記録
> 🔧 [対応者: 氏名] 修正内容
```

#### ループ終了条件

全指摘が対応完了し、レビュー者が「承認」コメントを追記した時点でループ終了。

```markdown
## 最終承認
> ✅ [レビュー者: 氏名] 全指摘対応完了。承認。
```

### 7.3 コード修正

**原則として人間が修正する**。以下の場面に限り、エージェントに修正を依頼する：

| 場面 | 使用エージェント | 入力 | 出力 |
|------|-----------------|------|------|
| レビュー指摘の修正案作成が難しい場合 | Senior Developer / Frontend Developer | レビューコメント + 該当コード | 修正案 |
| 既存コードとの互換性問題の原因調査 | Backend Architect | エラーログ + 関連コード | 原因候補 + 修正方針 |
| セキュリティ懸念の確認 | Security Engineer | 該当コード | 脆弱性評価 + 修正方針 |
| DBマイグレーションの安全性確認 | Backend Architect | マイグレーションコード + 既存スキーマ | 安全性評価 |

エージェントへの入力は**該当箇所のみ**に限定する。ファイル全体やプロジェクト全体のコードは渡さない。

### 7.4 人間共同確認

バックエンド・フロントエンドのレビューループが両方完了した時点で、実装コードをDocker環境に適用し、結合して手動で動作確認を行う。

| 確認種別 | 方法 | 対象 |
|----------|------|------|
| API動作 | curl でリクエスト/レスポンス確認 | バックエンド |
| 画面表示 | ブラウザで画面遷移・表示確認 | フロントエンド |
| レスポンシブ | 複数のビューポートサイズで確認 | フロントエンド |
| DBマイグレーション | アップ/ダウン実行確認、データ整合性確認 | バックエンド |
| 設定変更 | 環境変数設定の有効性確認 | バックエンド |
| 結合動作 | バックエンドAPIとフロントエンドの連携確認 | 両方 |

#### 確認手順（バックエンド側）

```bash
# Docker環境に実装コードを適用後、API動作確認
curl -X POST https://127.0.0.1/swordv3/deposit \
  -H "Content-Type: application/json" \
  -d '{"metadata": {...}}' \
  -v
```

#### 確認手順（フロントエンド側）

- ブラウザで対象URLにアクセス
- 画面設計書（Excel）のスクリーンショットと実際の画面を比較
- 各コンポーネントの動作（クリック、入力、遷移）を確認
- レスポンシブ対応を確認（デスクトップ、タブレット、スマホのビューポート）

#### 確認手順（結合）

- フロントエンドからバックエンドAPIを呼び出し、エンドツーエンドの動作を確認
- エラー発生時の画面表示とAPIレスポンスの整合性を確認

### 7.5 必要時のみ AI 支援

実装コードやレビューで不具合が見つかった場合、人間がまず確認する。原因特定が難しい場合に限り、エージェントに以下の情報を渡す：

- 不具合の再現手順
- エラーメッセージ・ブラウザコンソールの該当部分
- 対象実装コードの該当箇所
- 詳細設計書/画面設計書の期待仕様の該当箇所
- 既存コードとの干渉が疑われる場合の既存コード該当箇所

エージェントの出力は以下に限定する：

- 原因候補
- 設計書・実装の不整合箇所
- 修正方針
- 必要に応じた最小限の修正案

## 8. バックエンド・フロントエンドの並列実行

### 8.1 並列実行の基本方針

バックエンドとフロントエンドは、実装コード生成〜人間レビュー+修正ループを並列で実行する。
両方のレビューループが完了した時点で、人間が **バックエンド＋フロントエンドを結合して共同確認** を行う。

```
  Time →

  バックエンド:  [実装生成]→[レビューループ]→[待機]
  フロントエンド:[実装生成]→[レビューループ]→[待機]
                                          ↓
                              [人間共同確認（結合動作確認）]
```

### 8.2 並列実行における依存関係の処理

| 依存関係 | 処理方法 |
|----------|---------|
| API仕様の整合性 | 詳細設計書と画面設計書がAPI仕様で整合性が取れていることは設計段階で人間が担保済み |
| フロントエンドがバックエンド完了を待つ必要がある場合 | バックエンドのAPIエンドポイントが確定次第、フロントエンド実装を再開 |
| バックエンドがフロントエンドの依存を持つ場合 | 通常発生しない（バックエンドはAPIを提供する側） |

### 8.3 部分完了時の運用

片方のパイプラインが先に完了した場合、以下の対応を行う：

- 先に完了した側の変更を **独立したブランチ** で保持
- 後に完了した側も完了した後、両方を **統合ブランチ** にマージ
- 統合後に **両方の動作を合わせた結合確認** を行う（簡易的、詳細はテストパイプラインで実施）

### 9.1 ループ構造

```
  実装コード生成（エージェント）
        │
        ▼
  ┌──────────────┐
  │ 人間レビュー  │ ←─┐
  │              │    │
  │ 承認?        │    │
  │  ├── はい ──→ 待機（他方完了後・共同確認へ）  │

  ▼                            │

  │                            │
  ├── 人間が修正 ──────────────┘
  │
  └── エージェントが修正 ──────┘
      （必要時のみ）
```

### 9.2 レビュー→修正の1サイクル

| ステップ | 担当 | 動作 |
|----------|------|------|
| 1. レビュー | 人間 | 実装コードを設計書と照合し、問題点をコメントとして追記 |
| 2. 修正指示 | 人間 | 各問題点に対して修正指示を追記 |
| 3. 修正 | 人間 / エージェント | レビューコメントを読み込み、修正を適用 |
| 4. 修正報告 | 修正者 | 修正内容を追記 |
| 5. 再レビュー | 人間 | 修正内容を確認。OKなら承認、不十分なら再度修正指示 |

### 9.3 エージェント修正時の入力限定

エージェントに修正を依頼する場合、渡す情報は以下の最小限に限定する：

```
- レビューコメントの該当箇所
- 修正対象の関数・メソッド・コンポーネント
- 関連する設計書の該当箇所（必要時）
- 既存コードの該当箇所（patch pathやimport位置の確認用）
```

ファイル全体やプロジェクト全体のコードは渡さない。

## 11. エラーハンドリングとAI支援

### 11.1 共同確認失敗の分類

| 失敗タイプ | 原因例 | 対応 |
|-----------|--------|------|
| 実装ミスのロジックエラー | `AttributeError`, `KeyError` | 詳細設計書の処理フローを再確認 → 実装の修正 |
| API仕様の不整合 | `404 Not Found`, `405 Method Not Allowed` | 詳細設計書のエンドポイント定義を再確認 |
| DBマイグレーション失敗 | `OperationalError`, `ProgrammingError` | マイグレーションのアップ/ダウン定義を再確認 |
| フロントエンドの表示不具合 | コンポーネントの未定義、CSSの変数未定義 | 画面設計書、デザイン規約を再確認 |
| バックエンド・フロントエンド間の結合不具合 | APIレスポンスのJSON構造が画面と異なる | 詳細設計書と画面設計書のAPI仕様の整合性を再確認 |
| 既存コードとの干渉 | import循環、名前空間の競合 | 既存コードの影響範囲を調査 → 修正方針の決定 |
| 設定変更の反映ミス | 環境変数の未設定、configの未読み込み | 設定ファイルの修正とDockerの再起動 |

### 11.2 AI支援による原因調査

人間だけで原因特定または修正方針の判断が難しい場合に限り、エージェントに以下の情報を渡す：

- 失敗した処理の内容と再現手順
- エラーメッセージ・スタックトレースの該当部分
- 対象実装コードの該当箇所
- 詳細設計書/画面設計書の期待仕様の該当箇所
- 既存コードとの干渉が疑われる場合の既存コード該当箇所

エージェントの出力は以下に限定する：

- 原因候補
- 設計書・実装の不整合箇所
- 修正方針
- 必要に応じた最小限の修正案

> **利用シーン**: 既存コードとの干渉が複雑な場合、Invenio3のフレームワーク内部の動作が不明な場合、DBマイグレーションの失敗原因の切り分けに時間がかかる場合、設計書・実装のどこに不整合があるか整理したい場合

## 12. テストパイプラインとの連携

### 12.1 連携フロー

```
  [実装パイプライン完了後]
        │
        ▼  実装コード + 変更ファイル一覧
  [テストパイプライン]

  詳細設計書 ──────────────→  ① 詳細設計書読み込み
                                Backend Architect
                                ↓
                            ② テスト仕様書生成
                                ↓
                            🔴 人間レビュー #1
                                ↓
                            ③ テストコード生成
                                ← 実装コードを参照（patch path, 関数名, import位置）
```

実装パイプラインが完了した実装コードを、テストパイプラインのBackend Architectが **必要最小限** 参照してテスト仕様書・テストコードを生成する。

### 12.2 実装コードの参照範囲（テストパイプライン）

テストパイプラインのBackend Architectが実装コードを参照する範囲は以下に限定する：

| 参照項目 | 目的 | 範囲 |
|----------|------|------|
| patch path | モック対象のフルパス特定 | import文、モジュールパス |
| 関数名・メソッド名 | テストメソッドの命名 | 関数定義行 |
| import位置 | patch pathの基本原則に従ったパス決定 | import文 |
| fixture利用可否 | 既存フィクスチャの活用確認 | `conftest.py` |

> **注意**: テストパイプラインの詳細は [ai_test_pipeline.md](ai_test_pipeline.md) を参照。実装コードは「必要最小限」の参照に限定し、実装追認型のテストにならないようにする。

### 12.3 フロントエンド実装と結合テストの連携

```
  フロントエンド実装完了
        │
        ▼
  結合テストパイプライン
        │
        ├── EvidenceQA（agent-browser）で画面動作検証
        ├── 証跡収集（5種を照合）
        │     ├── スクリーンショット
        │     ├── ブラウザ開発者コンソール（コンソールエラー有無・APIリクエスト/レスポンス）
        │     ├── DBテーブルのレコード状況
        │     ├── コンテナログ
        │     └── DBログ
        └── Reality Checkerで最終判定
```

#### 結合テストの証跡定義（概要）

結合テストの証跡は、スクリーンショット単独ではなく、以下の **5種の証跡** を相互に照合して判定する。

| 証跡 | 内容 |
|------|------|
| スクリーンショット | 画面表示・操作結果の視覚的証拠 |
| ブラウザ開発者コンソール | コンソールエラーの有無、APIリクエスト/レスポンスの内容 |
| DBテーブルのレコード状況 | 操作によるレコードの登録・更新・削除結果 |
| コンテナログ | バックエンド（webコンテナ等）のアプリケーションログ |
| DBログ | DB側で記録されたクエリ・エラーのログ |

- **正常系**: フロント・バックエンド双方にエラーがなく、処理が正常実行されている様子（コンソールエラーなし・期待どおりのAPIレスポンス・想定どおりのDBレコード変化・ログ上の異常なし）を証跡とする
- **異常系**: 期待されるエラー表示・エラーレスポンス・ロールバック後のDB状態・ログ上の想定内エラーといった、異常系として正しく振る舞っている根拠を証跡とする
- **スクリーンショット単独での合格判定は不可**とする。画面が正しく見えても、コンソール・DB・ログのいずれかに想定外の異常があれば合格としない

> **注意**: 5種の証跡の詳細な収集ルール・判定基準（PASS / NEEDS WORK）は [ai_test_pipeline.md](ai_test_pipeline.md) を参照。本節は実装パイプライン側からの概要整合にとどめる。

## 13. 機能仕様書更新フェーズ

### 13.1 フェーズの位置づけ

**タイミング**: テストパイプライン（単体テスト・結合テスト）の完了後、リリース前

テストパイプラインが完了し、動作確認済みの実装が確定した時点で機能仕様書を更新する。この順序を採用する理由は以下の通り：

- テスト工程でも仕様変更が発覚した場合、仕様書を複数回修正するリスクを回避できる
- 動作確認済みの実装に基づいて仕様書を書くことで、「書いた仕様と実際の動作が異なる」事態を防げる
- テストパイプラインの最終確認（全テスト PASS・カバレッジ基準充足）をもって仕様書更新の開始条件とすることで、仕様書更新忘れのままリリースするリスクを制度的に防止する

### 13.2 担当者と役割分担

| 担当 | 役割 |
|------|------|
| 🤖 エージェント | 詳細設計書の変更ファイル一覧と `SUMMARY.md` を参照し、更新が必要な仕様書ファイルを特定する。各ファイルについて差分案（どの行をどう修正するか）を生成する |
| 🔴 人間 | エージェントが生成した差分案をレビューし、内容が正確かつ適切であることを確認する。確認後、weko-document リポジトリに feature ブランチを作成し、PR を作成・マージする |

仕様書の内容判断（追記・削除・変更の妥当性）は人間が最終責任を持つ。エージェントの出力はあくまで草案であり、そのまま使用せず必ずレビューする。

### 13.3 更新対象ファイルの特定方法

**ステップ1: 詳細設計書から変更内容を把握する**

詳細設計書のセクション1「変更ファイル一覧」を参照し、今回の案件で変更したファイル・機能を把握する。

**ステップ2: SUMMARY.md を参照して対応する仕様書ファイルを特定する**

エージェントは `weko-document` リポジトリの `SUMMARY.md`（honkit のエントリポイント）を参照し、変更内容に対応する仕様書ファイルを特定する。

```
weko-document リポジトリのファイル構成:
  docs/spec/base/
    ├── user/USER_X_X.md   ← ユーザ機能仕様（例: USER_10_1.md = ワークスペース：アイテム一覧）
    ├── admin/ADMIN_X_X.md ← 管理機能仕様
    └── api/API_XX.md      ← Web API 仕様
  docs/spec/base/api/<機能名>.yaml  ← OpenAPI 定義（SUMMARY.md の外にある場合あり）
```

**ステップ3: 更新が不要なファイルを除外する**

変更ファイル一覧に記載されていても、内部リファクタリングや設定変更のみで外部から見た機能仕様に変化がない場合は仕様書更新不要と判断する。

### 13.4 エージェントへの指示テンプレート

以下のテンプレートをエージェントへの指示として使用する：

```
## 機能仕様書更新草案の生成

### 入力情報
- 詳細設計書: `docs/cases/<案件名>/detailed_design.md`（Read ツールで読み込む）
- weko-document SUMMARY.md のパス: <記載すること>
- 対象の機能仕様書ファイルのパス: <記載すること>
- 変更の概要: <今回の案件で変更した機能の概要を一言で記述>

### 依頼内容
1. 詳細設計書（`docs/cases/<案件名>/detailed_design.md`）のセクション1「変更ファイル一覧」と各機能仕様を Read ツールで読み込んでください
2. 上記の SUMMARY.md を Read ツールで読み込み、変更内容に対応する仕様書ファイルを確認してください
3. 上記の機能仕様書ファイルを Read ツールで読み込んでください
   - **SUMMARY.md 以外のファイルは指定されたもののみを読む。リポジトリ全体を走査しないこと**
4. 各仕様書ファイルについて、以下の形式で差分案を生成してください。
   差分案を生成する際は以下を厳守すること：
   - 既存の機能仕様書の記述スタイル・粒度を維持する
   - 内部実装の詳細（関数の引数型・サンプルコード・例外クラス名・DBカラムの型定義）は機能仕様書に含めない
   - 「機能として何ができるか・どう動作するか」の外部仕様のみを記述する
   - 外部仕様に変化がない場合（内部実装の整備・リファクタリングのみ）は「変更不要」と明示する

#### 差分案の形式

**対象ファイル**: `docs/spec/base/user/USER_X_X.md`
**変更種別**: 追記 / 修正 / 削除 / 変更不要

```diff
- （削除または変更前の行）
+ （追記または変更後の行）
```

**変更理由**: （詳細設計書の該当箇所と対応する仕様変更の説明。変更不要の場合はその根拠を記述）

4. OpenAPI YAML ファイルの更新要否も判断し、更新が必要な場合は同様に差分案を生成してください
5. 更新対象ファイルの一覧を最初にまとめて提示してください
```

### 13.5 人間のレビュー・PR 作成フロー

エージェントが差分案を生成した後、人間は以下の手順で対応する：

| ステップ | 担当 | 内容 |
|---------|------|------|
| 1. 差分案のレビュー | 🔴 人間 | エージェントの差分案が実際の変更内容と一致しているか確認する。仕様書の記述スタイル・粒度が既存ファイルと統一されているか確認する |
| 2. 差分の修正 | 🔴 人間 | 不正確・不足・過剰な箇所を修正する |
| 3. feature ブランチ作成 | 🔴 人間 | weko-document リポジトリで `feature/<課題ID>` ブランチを作成する |
| 4. 仕様書ファイルの編集 | 🔴 人間 | レビュー済みの差分を各ファイルに適用する |
| 5. PR 作成 | 🔴 人間 | `develop` ブランチへの PR を作成する |
| 6. PR マージ | 🔴 人間 | レビュー後に `develop` へマージする |

> **注意**: weko-document は別 GitHub リポジトリ（`https://github.com/RCOSDP/weko-document`）のため、weko 本体のブランチとは独立して管理する。ブランチ戦略は `feature/<課題ID>` → `develop` → `main` の流れに従う。

### 13.6 OpenAPI YAML ファイルの更新判断基準

以下の変更を伴う案件では、Markdown 仕様書の更新に加えて OpenAPI YAML ファイルの更新も必要となる：

| 変更内容 | 更新要否 | 対象ファイル |
|---------|---------|------------|
| API エンドポイントの追加・削除 | 必須 | `docs/spec/base/api/<機能名>.yaml` |
| リクエスト・レスポンスの JSON スキーマ変更 | 必須 | `docs/spec/base/api/<機能名>.yaml` |
| HTTP メソッド・URLパスの変更 | 必須 | `docs/spec/base/api/<機能名>.yaml` |
| 認証・認可方式の変更 | 必須 | `docs/spec/base/api/<機能名>.yaml` |
| 内部ロジックの変更のみ（API仕様に変化なし） | 不要 | — |
| フロントエンドのUI変更のみ | 不要 | — |
| 設定値・定数の追加のみ | 原則不要（管理機能仕様書に追記） | — |

OpenAPI YAML は Markdown 仕様書とは別ファイルで管理されており、`SUMMARY.md` のエントリポイント外に配置される場合があるため注意する。

## 14. マニュアル更新フェーズ

### 14.1 フェーズの位置づけ

**タイミング**: 機能仕様書更新フェーズ（13章）の完了後、リリース前

機能仕様書の更新が確定した時点でマニュアルを更新する。マニュアルは **weko-document リポジトリ内** に存在する。この順序（機能仕様書更新 → マニュアル更新）を制度化する理由は以下の通り：

- 機能仕様の確定後にマニュアルを更新することで、仕様とマニュアルの不整合を防げる
- 仕様書更新とマニュアル更新を別工程として明示することで、マニュアル更新漏れのままリリースするリスクを制度的に防止できる
- 機能仕様書更新フェーズ（13章）で特定済みの「外部から見た操作・画面の変化」を起点にできるため、マニュアル更新対象の特定が効率化される

```
  機能仕様書更新（13章）完了
        │
        ▼
  ③ マニュアル更新（weko-document への PR）
        │
        ├── 🤖 エージェント: マニュアル差分草案を生成
        └── 🔴 人間: レビュー・修正・PR作成・マージ
        │
        ▼
  リリースへ
```

### 14.2 担当者と役割分担

機能仕様書更新フェーズ（13章）と **同じパターン** で実施する。

| 担当 | 役割 |
|------|------|
| 🤖 エージェント | 詳細設計書の変更内容と weko-document の構成（`SUMMARY.md` 等）を参照し、更新が必要なマニュアルファイルを特定する。各ファイルについて差分草案（どの行をどう修正するか）を生成する |
| 🔴 人間 | エージェントが生成した差分草案をレビューし、内容が正確かつ適切であることを確認する。確認後、weko-document リポジトリに feature ブランチを作成し、PR を作成・マージする |

マニュアルの内容判断（追記・削除・変更の妥当性）は人間が最終責任を持つ。エージェントの出力はあくまで草案であり、そのまま使用せず必ずレビューする。

### 14.3 更新対象ファイルの特定方法

13.3 節の手順に倣い、以下の手順で更新対象マニュアルを特定する。

**ステップ1: 詳細設計書から変更内容を把握する**

詳細設計書のセクション1「変更ファイル一覧」と各機能仕様を参照し、今回の案件で変更した機能・操作・画面を把握する。

**ステップ2: weko-document の構成を参照して対応するマニュアルファイルを特定する**

エージェントは `weko-document` リポジトリの `SUMMARY.md`（honkit のエントリポイント）を参照し、変更内容に対応するマニュアルファイルを特定する。

```
weko-document リポジトリのマニュアル構成（例）:
  docs/manual/
    ├── user/    ← 利用者向けマニュアル（操作手順・画面説明）
    ├── admin/   ← 管理者向けマニュアル
    └── images/  ← 操作画面のスクリーンショット等
```

**ステップ3: 更新が不要なファイルを除外する**

外部から見た操作手順・画面に変化がない内部変更のみ（内部リファクタリング・設定値変更・API内部ロジックのみの変更など）の場合は、マニュアル更新不要と判断し「変更不要」と明示する。

### 14.4 エージェントへの指示テンプレート

以下のテンプレートをエージェントへの指示として使用する：

```
## マニュアル更新草案の生成

### 入力情報
- 詳細設計書: `docs/cases/<案件名>/detailed_design.md`（Read ツールで読み込む）
- weko-document SUMMARY.md のパス: <記載すること>
- 対象のマニュアルファイルのパス: <記載すること>
- 変更の概要: <今回の案件で変更した操作・画面の概要を一言で記述>

### 依頼内容
1. 詳細設計書（`docs/cases/<案件名>/detailed_design.md`）のセクション1「変更ファイル一覧」と各機能仕様を Read ツールで読み込んでください
2. 上記の SUMMARY.md を Read ツールで読み込み、変更内容に対応するマニュアルファイルを確認してください
3. 上記のマニュアルファイルを Read ツールで読み込んでください
   - **SUMMARY.md 以外のファイルは指定されたもののみを読む。リポジトリ全体を走査しないこと**
4. 各マニュアルファイルについて、以下の形式で差分草案を生成してください。
   差分草案を生成する際は以下を厳守すること：
   - 既存のマニュアルの記述スタイル・粒度・トーン（利用者目線の操作手順）を維持する
   - 内部実装の詳細（関数・例外クラス名・DBカラムの型定義・サンプルコード）はマニュアルに含めない
   - 「利用者が何をどう操作するか・画面がどう見えるか」の操作手順のみを記述する
   - 外部から見た操作手順・画面に変化がない場合（内部変更のみ）は「変更不要」と明示する
   - スクリーンショットの差し替えが必要な箇所は、差し替えが必要である旨を注記する（画像生成は行わない）

#### 差分草案の形式

**対象ファイル**: `docs/manual/user/<ファイル名>.md`
**変更種別**: 追記 / 修正 / 削除 / 変更不要

```diff
- （削除または変更前の行）
+ （追記または変更後の行）
```

**変更理由**: （詳細設計書および機能仕様書の該当箇所と対応するマニュアル変更の説明。変更不要の場合はその根拠を記述）
**スクリーンショット差し替え要否**: 要 / 不要（要の場合は対象画像を記述）

4. 更新対象ファイルの一覧を最初にまとめて提示してください
```

差分草案はあくまで草案であり、最終的な内容の妥当性は人間が責任を持つ。エージェントはマニュアルファイルを直接編集せず、草案の提示までを担当する。

### 14.5 人間のレビュー・PR 作成フロー

エージェントが差分草案を生成した後、人間は以下の手順で対応する：

| ステップ | 担当 | 内容 |
|---------|------|------|
| 1. 差分草案のレビュー | 🔴 人間 | エージェントの差分草案が実際の操作・画面変更と一致しているか確認する。マニュアルの記述スタイル・粒度・トーンが既存ファイルと統一されているか確認する |
| 2. 差分の修正 | 🔴 人間 | 不正確・不足・過剰な箇所を修正する。必要なスクリーンショットを差し替える |
| 3. feature ブランチ作成 | 🔴 人間 | weko-document リポジトリで `feature/<課題ID>` ブランチを作成する |
| 4. マニュアルファイルの編集 | 🔴 人間 | レビュー済みの差分を各ファイルに適用する |
| 5. PR 作成 | 🔴 人間 | `develop` ブランチへの PR を作成する |
| 6. PR マージ | 🔴 人間 | レビュー後に `develop` へマージする |

> **注意**: weko-document は別 GitHub リポジトリ（`https://github.com/RCOSDP/weko-document`）のため、weko 本体のブランチとは独立して管理する。ブランチ戦略は `feature/<課題ID>` → `develop` → `main` の流れに従う。機能仕様書更新フェーズ（13章）と同一リポジトリのため、両フェーズの変更を同一の feature ブランチ・PR にまとめることも可能だが、その場合も「仕様書更新 → マニュアル更新」の順序で内容を確定させること。

# 付録

## A. 実装パイプライン vs テストパイプライン の比較

| 項目 | 実装パイプライン | テストパイプライン（単体） | テストパイプライン（結合） |
|------|-----------------|------------------------|------------------------|
| 入力 | 詳細設計書 / 画面設計書(xlsx) | 詳細設計書 | Excelテスト仕様書 |
| エージェント主担当 | 実装コード生成 | テスト仕様書・テストコード生成 | ブラウザ操作実行 |
| 使用エージェント | Senior Developer, Frontend Developer | Backend Architect | EvidenceQA, Code Reviewer |
| レビュー | 人間（任意回数） | 人間（2回固定） | 人間（1回） |
| 修正 | 人間中心、必要時にエージェント | 人間 | Code Reviewer |
| 確認手段 | 結合動作確認（手動） | pytest, coverage | スクリーンショットエビデンス |
| 共同確認 | 人間 | 人間 | Reality Checker |
| 並列実行 | バックエンド・フロントエンド並列 | 単体テストのみ | 結合テストのみ |

## B. 画面設計書（Excel）の読込方法

### xlsxスキルによる読込

画面設計書は Excel (`.xlsx`) 形式で配置する（配置先は [../../CLAUDE.md](../../CLAUDE.md)「ドキュメントディレクトリ構成」を参照）。Frontend Developerは **xlsxスキル** を使用して直接読み込む。

**読込方法**:

```
xlsxスキルでファイルパスを指定して読み込み:
  docs/cases/<案件名>/ui_design.xlsx
```

**Excelの想定シート構成**:

| シート名 | 内容 |
|----------|------|
| 画面一覧 | 画面名、URL、対応モジュール、備考 |
| <画面名> | コンポーネントNo、コンポーネント名、タイプ、位置、動作、表示条件、スクリーンショット参照 |

**読込時の注意**:
- スクリーンショット画像はExcel内に埋め込まれている場合、xlsxスキルではテキスト・表データとして読み込める部分のみ取得可能
- スクリーンショットの詳細を確認する必要がある場合は、別途画像ファイルとして配置することを推奨
- 表形式のコンポーネント一覧はxlsxスキルで正確に取得可能

### 変換不要の理由

- テストパイプラインの結合テストでは Excel → Markdown の変換が必要だが、実装パイプラインではxlsxスキルで直接読込可能
- 変換工程を省略することで、変換ミスのリスクを排除し、Excelの最新状態を常にエージェントが参照できる
