## 3. 設計工程

### 3.1 基本設計書の作成

**担当**: 🔴 人間  
**入力**: なし（起点）  
**出力**: `docs/cases/<案件名>/basic_design.md`

| 作業 | 内容 |
|------|------|
| 背景・目的の定義 | 現状の問題点と改修で達成したいことを記述 |
| スコープの確定 | 今回やること（3.1）と対象外（3.2）を明示。対象外の明示はAIの善意のスコープ逸脱を防ぐ |
| 機能要件の記述 | 各機能の処理概要・エラー処理・**完了条件**（振る舞いベースで記述）を定義 |
| 非機能要件の記述 | パフォーマンス・セキュリティ・後方互換性・ログ方針を定義 |

> **完了条件の書き方**: 「〜が呼ばれること」ではなく「〜が返ること」「〜がDBに記録されること」の形式で記述する。これにより単体テストが実装追認型にならない。  
> 参考: [ai_review_criteria.md](ai_review_criteria.md) 観点6

---

### 3.2 詳細設計書（全機能まとめ版）の作成

**担当**: 🔴 人間  
**入力**: 基本設計書  
**出力**: `docs/cases/<案件名>/detailed_design.md`

| 作業 | 内容 |
|------|------|
| 変更ファイル一覧の記述 | 新規・修正・削除するファイルを全て列挙（AIが変更してよいファイルの定義） |
| 関数仕様の記述 | 引数・戻り値・処理仕様・エラーハンドリングを記述 |
| エラーハンドリング表の記述 | 条件・例外クラス・**メッセージ文言（完成形）** を記述。AIによる文言の言い換えを防ぐ |
| 実装判断ポイントの明示 | 曖昧になりうる箇所にコードスニペット付きで指針を記述 |
| 設定値仕様の記述 | 設定キー名・デフォルト値・配置ファイルを明記 |

> **実装判断ポイントの重要性**: 記述が不足すると、AIが自己判断で補完し設計意図とずれた実装になる。  
> 参考: [ai_review_criteria.md](ai_review_criteria.md) 観点2

---

### 3.3 画面設計書（Excel）の作成

**担当**: 🔴 人間  
**入力**: 基本設計書  
**出力**: `docs/cases/<案件名>/ui_design.xlsx`

| 作業 | 内容 |
|------|------|
| 画面一覧の作成 | 画面名・URL・対応モジュールを一覧化 |
| 画面ごとの仕様記述 | コンポーネント一覧・レイアウト・動作仕様・表示条件を記述 |
| API仕様の整合性確認 | 詳細設計書のAPIエンドポイント・JSONレスポンス構造と一致することを確認 |

---

### 3.4 詳細設計書の分割

**担当**: 🤖 Claude（分割エージェント）  
**入力**: `detailed_design.md`、`detailed_design_split_rules.md`  
**出力**: `docs/cases/<案件名>/detailed_design_NN_<機能名>.md`（N 個）

| 作業 | 内容 |
|------|------|
| 実装単位の判定 | 関数数・ステップ数・新規ファイル数・依存関係を基に分割単位を決定 |
| 依存関係の分析 | 実装単位間の呼び出し関係・import 関係を整理（内部推論。ファイル出力不要） |
| トポロジカル順序での番号付与 | 依存先の NN ＜ 依存元の NN になるよう番号を付与 |
| 分割ファイルの生成 | 各ファイル先頭に「実装単位メタ情報」（前提とする実装単位・推定ステップ数）を付与 |

> 依存関係が複雑な大規模案件では、番号確定前に十分時間をかけて依存関係を整理する。  
> 詳細: [detailed_design_split_rules.md](detailed_design_split_rules.md)

## 4. 実装工程

バックエンドとフロントエンドは並列実行する。両方のレビューループ完了後にセキュリティレビューを行う（結合動作確認・結合テストは後続工程。実装コードレビュー後の順序は「セキュリティレビュー → 単体テスト → 結合動作確認 → 結合テスト」となる）。

> **Git 運用方針**: 実装コード本体のコミット・プッシュは 🔴 人間が行う。Claude はコミットを行わない（行えない）。これは weko-document 側（セクション8）の人間による PR フローとは別に、実装コード本体についても同様である。

### 4.1 実装コード生成（バックエンド）

**担当**: 🤖 Claude（Senior Developer）  
**入力**: 分割詳細設計書（1 ファイル = 1 セッション）、コーディング規約、既存コード  
**出力**: 実装 `.py` ファイル、DB マイグレーション、設定変更

| 作業 | 内容 |
|------|------|
| 前提実装単位の確認 | メタ情報の「前提とする実装単位」が完了していることを確認してから着手 |
| 設計書厳守での実装 | 処理フロー・インターフェース・エラーハンドリングを設計書通りに実装。設計書にない機能は実装しない |
| 既存コードとの整合性確保 | 既存の import スタイル・クラス設計パターンを踏襲 |
| レビュー記録表の雛形生成 | `docs/cases/<案件名>/implementation_review.md` に雛形を生成 |

---

### 4.2 実装コード生成（フロントエンド）

**担当**: 🤖 Claude（Frontend Developer）  
**入力**: 画面設計書（xlsx スキルで直接読込）、デザイン規約、既存コード  
**出力**: `.jsx`、`.html`、`.scss` ファイル

| 作業 | 内容 |
|------|------|
| 画面設計書の読込 | xlsx スキルで Excel を直接読み込み（Markdown への変換工程は不要） |
| 設計書厳守での実装 | レイアウト・コンポーネント・状態遷移・UI 動作を設計書通りに実装 |
| デザイン規約の遵守 | Sass 変数・コンポーネントパターン・グリッドシステムに従う |

---

### 4.3 実装コードレビュー

**担当**: 🔴 人間  
**入力**: 実装コード、設計書、`implementation_review.md`  
**出力**: レビューコメント付き `implementation_review.md`（承認 or 修正指示）

| 確認観点 | 内容 |
|---------|------|
| 変更ファイルの範囲 | 詳細設計書「変更ファイル一覧」に記載のないファイルが変更されていないか |
| 設計書整合性 | 処理フロー・インターフェース・エラーメッセージ文言が設計書と一致しているか |
| スコープ逸脱 | 設計書にない機能・バリデーション・リファクタリングが混入していないか |
| API・メソッドの実在確認 | インポートしているクラス・メソッド・キーワード引数が実際に存在するか |
| 識別子・文字列の一致 | 関数名・設定キー・エラーメッセージが設計書の完成形と一字一句一致しているか |
| 既存コードとの互換性 | 既存 API の breaking change がないか、import 循環がないか |
| セッション間の不整合 | 前の分割単位の関数シグネチャと今回の呼び出しが一致しているか |

> AIに生成を委託することで固有に生じるリスクの詳細は [ai_review_criteria.md](ai_review_criteria.md) を参照。

---

### 4.4 実装コード修正

**担当**: 🔴 人間（主）/ 🤖 Claude（必要時のみ）

## 5. 単体テスト工程

> **本工程はバックエンド専用である**。フロントエンドの単体テストは実施しない。これは意図的な判断であり、フロントエンドの品質確認は結合テスト工程（セクション7）で担保する。

### 5.1 テスト仕様書生成

**担当**: 🤖 Claude（Backend Architect）  
**入力**: 詳細設計書（主入力）、実装コード（最小限の参照のみ）  
**出力**: `<モジュール>_test_spec.md`

| 作業 | 内容 |
|------|------|
| テスト観点の整理 | 詳細設計書から条件分岐・外部依存・例外ハンドラを抽出 |
| 分岐 ID の付与 | 全条件分岐に B01, B02, ... の識別子を付与 |
| テストケース表の生成 | ケース ID・テスト内容・入力・期待結果・モック対象を記述 |
| モック対象一覧表の生成 | モジュールパスとモック理由を記述 |
| 分岐マップの生成 | 各分岐 ID × True/False × 対応ケース ID を対応付け |

> **注意**: 実装コードを主入力にすると実装追認型のテストになる。設計書を主入力とし、実装コードは patch path・関数名・import 位置・fixture 利用可否の確認のみに限定する。

---

### 5.2 テスト仕様書レビュー（レビュー #1）

**担当**: 🔴 人間  
**入力**: テスト仕様書  
**出力**: コメント付き修正指示、または承認

| 確認観点 | 内容 |
|---------|------|
| 分岐網羅性 | 全分岐 ID に対応するテストケースが揃っているか |
| テストケースの妥当性 | 実装の内部フローではなく外から見た振る舞いで記述されているか |
| 異常系・境界値 | 正常系だけでなく異常系・境界値のケースが含まれているか |
| 完了条件との対応 | 基本設計書の完了条件・詳細設計書のエラーハンドリングに対応するケースが揃っているか |

---

### 5.3 テストコード生成

**担当**: 🤖 Claude（Backend Architect）  
**入力**: 承認済みテスト仕様書、`conftest.py`、実装コード（最小限）  
**出力**: `tests/test_<モジュール名>.py`

| 作業 | 内容 |
|------|------|
| pytest コードの生成 | 1 テストケース = 1 メソッド、`Test<TargetMethodName>` クラスにまとめる |
| patch path の設定 | テスト対象モジュール内でその名前が参照されているパスを指定 |
| fixture の活用 | `conftest.py` の既存 fixture を優先使用 |

---

### 5.4 テストコードレビュー（レビュー #2）

**担当**: 🔴 人間  
**入力**: テストコード  
**出力**: コメント付き修正指示、または承認

| 確認観点 | 内容 |
|---------|------|
| テスト対象のモック | テスト対象そのものをモックしていないか |
| アサーションの妥当性 | `assert result is not None` だけで終わっていないか |
| patch path の正確性 | 定義元ではなく参照元のパスになっているか |
| モックの検証範囲 | 「呼ばれたか」だけでなく「返却値・副作用」も検証しているか |

## 7. 結合テスト工程

### 7.1 ブラウザ操作テスト実行

**担当**: 🤖 Claude（EvidenceQA + agent-browser）  
**入力**: Excel テスト仕様書（xlsx スキルで直接読込）  
**出力**: スクリーンショットエビデンス（各ステップ）、問題リスト

| 作業 | 内容 |
|------|------|
| テスト仕様書の読込 | Excel テスト仕様書を xlsx スキルで直接読み込む（Markdown への変換工程は不要） |
| テストシナリオの読み込み | テスト仕様書の各ステップを順次実行 |
| ブラウザ操作の実行 | ナビゲーション・フォーム入力・クリックを agent-browser で自動実行 |
| スクリーンショットの収集 | 各ステップ後・テストケース開始・終了・失敗時にキャプチャ |
| 問題の報告 | 証拠（スクリーンショット）で示せる問題のみを報告する。問題が見つからない場合はその旨を報告する |

---

### 7.2 問題分析・修正指示

**担当**: 🤖 Claude（Code Reviewer）（分析・指示）/ 🔴 人間（修正の差し戻し・再テスト）  
**入力**: スクリーンショット、問題リスト  
**出力**: 原因分析、修正指示

EvidenceQA のスクリーンショットを基に原因を分析し、修正指示を出す。最大3回のループを繰り返す。

- **コード修正の担当**: Code Reviewer が出した修正指示に基づき、コード修正は 🔴 人間が Senior Developer に差し戻して実施する。
- **修正コードのレビュー**: Senior Developer による修正後、その修正コードに対して 🔴 人間がレビューを行う。レビュー観点は実装コードレビュー（4.3）と同様（設計書整合性・スコープ逸脱・既存コードとの互換性など）でよい。
- **回帰テスト**: 結合テストでコード修正が発生した場合、🔴 人間が単体テスト（pytest）を再実行する。再実行の担当は人間であり、Claude は実行しない。修正コードのレビュー → 必要に応じた単体テスト再実行、という順で行う。
- **エスカレーション**: 最大3回ループを超過した場合、または 7.3 で NEEDS WORK 判定が出た場合は、🔴 人間が判断し、実装工程（セクション4）へ差し戻す。

---

### 7.3 最終検証

**担当**: 🤖 Claude（Reality Checker）  
**入力**: 全スクリーンショットエビデンス  
**出力**: PASS / NEEDS WORK 判定

全エビデンスを確認し、証拠ベースで最終判定を行う。デフォルトは「NEEDS WORK」。PASS を出すには圧倒的な証拠が必要。NEEDS WORK 判定が出た場合は、🔴 人間が判断し実装工程（セクション4）へ差し戻す。

## 8. 機能仕様書更新工程

テストパイプライン（単体テスト・結合テスト）の完了後、リリース前に実施する。動作確認済みの実装に基づいて weko-document リポジトリの機能仕様書を更新することで、仕様書と実装の乖離を防ぐ。

詳細な手順・エージェントへの指示テンプレート・OpenAPI YAML の更新判断基準は [ai_implementation_pipeline.md](ai_implementation_pipeline.md) のセクション13を参照。

### 8.1 更新対象ファイルの特定・差分案生成

**担当**: 🤖 Claude（Spec Updater）  
**入力**: 詳細設計書（変更ファイル一覧・各機能仕様）、weko-document の `SUMMARY.md`、最終的な git diff（実装コードの実差分）  
**出力**: 更新対象ファイル一覧、各ファイルの差分案

| 作業 | 内容 |
|------|------|
| 変更内容の把握 | 詳細設計書のセクション1「変更ファイル一覧」から変更した機能を確認する |
| 実差分との突き合わせ | レビュー修正を経た実コードは設計書から乖離しうるため、実際のコード差分（git diff）と設計書を突き合わせて変更内容を確定する |
| 対応仕様書ファイルの特定 | SUMMARY.md を参照し、変更内容に対応する `USER_X_X.md`・`ADMIN_X_X.md`・`API_XX.md` を特定する |
| 差分案の生成 | 各仕様書ファイルについて追記・修正・削除の差分案（diff 形式）を、設計書と git diff の両方に整合する形で生成する |
| OpenAPI YAML の判断 | API エンドポイント・スキーマ変更を伴う場合、対応する `.yaml` ファイルの差分案も生成する |

---

### 8.2 差分案レビュー・PR 作成・マージ

**担当**: 🔴 人間  
**入力**: エージェントが生成した差分案  
**出力**: weko-document への PR（`develop` ブランチへのマージ）

| 作業 | 内容 |
|------|------|
| 差分案のレビュー | 差分案が実際の変更内容と一致しているか、記述スタイル・粒度が既存ファイルと統一されているかを確認する |
| 差分の修正 | 不正確・不足・過剰な箇所を人間が修正する |
| ブランチ・PR の作成 | weko-document リポジトリで `feature/<課題ID>` ブランチを作成し、仕様書ファイルを編集して PR を作成する |
| PR のマージ | レビュー後に `develop` ブランチへマージする |
