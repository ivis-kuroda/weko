# 詳細設計書の分割ルール

**ステータス**: 設計確定版
**関連ドキュメント**: [ai_implementation_pipeline.md](ai_implementation_pipeline.md)

---

## 1. 分割の目的

分割は以下の2つの目的を同時に達成するために行う。

**① トークン管理**  
1つの詳細設計書に全機能を記載すると、実装セッション開始時に設計書の読み込みと実装の両方でトークンを消費し、セッション途中でトークン上限に達するリスクがある。
「1分割ファイル = 1実装セッション」を原則とし、実装エージェントが確実に1セッション内で完結できる粒度に分割する。

**② 依存関係を考慮した実装順序の確定**  
依存先のメソッド・クラスが必ず先の実装単位として完了した状態でレビューが行われるよう、分割と番号付けをセットで設計する。
これにより「実装単位 01 のレビュー時点で、01 が呼び出す前提メソッドは既存コードまたは前の実装単位で実装済み」という状態を保証する。

## 2. 分割フェーズ

```
[人間] 詳細設計書（全機能まとめ版）を作成
  ↓
[Claude] 分割エージェント: detailed_design.md を読み込み、分割単位を判定して分割ファイルと一覧ファイルを生成
  → detailed_design_NN_*.md（各実装単位）
  → split_index.md（実装単位の一覧・依存関係・進捗管理）
  ↓
[Claude] 実装エージェント × N: 各 detailed_design_NN_*.md を独立したセッションで実装
  → 完了時に split_index.md の実装状況を更新
```

分割はオーケストレーターが「分割エージェント」を起動することで実施する。人間が手動で分割する必要はない。

## 3. 分割基準

以下のいずれかに該当する場合、その関数群を別の実装単位として分割する。

| 基準 | 目安 | 理由 |
|------|------|------|
| 1ファイルに含まれる関数数 | 4関数以上 | 関数ごとの処理仕様・エラーハンドリングがトークンを圧迫する |
| 処理仕様の合計ステップ数 | 20ステップ以上 | コードスニペット・擬似コードの量が増加する |
| 新規作成ファイル数 | 2ファイル以上 | ファイル間の依存関係が複雑になる |
| 他の実装単位への依存 | 依存関係あり | 依存先を先に実装する必要があるため別単位に分離 |

上記に該当しない場合（小規模な改修）は分割不要。`detailed_design.md` 1ファイルのまま実装する。

### 依存順序の決定

分割後、各実装単位間の依存関係を洗い出し、**NN 番号をトポロジカル順序で付与する**。

| ルール | 例 |
|--------|-----|
| 実装単位 A の関数が実装単位 B の関数を呼び出す場合、B を先に（小さい NN に）置く | `register()` が `send_registration_email()` を呼ぶ → `send_registration_email` を 01 に |
| 実装単位 A が実装単位 B で新規作成されるクラス・モジュールを import する場合、B を先に置く | 新規クラス定義が先、その利用者が後 |
| 循環依存がある場合は、共通インターフェースまたはスタブを別単位として先行させて解消する | 共通定数・例外クラスの定義を 01 に切り出す |

> **確認基準**: 実装単位 NN のレビューを行う時点で、NN が依存する全てのメソッド・クラスが「既存コード」または「NN より小さい番号の実装単位」に含まれていること。

## 4. 分割ファイルの形式

### 4.1 ファイル命名規則

```
docs/cases/<案件名>/detailed_design_NN_<機能名>.md
```

- `NN` は `01` から始まる2桁の連番。依存関係のトポロジカル順序に従って付与する（依存先の番号 ＜ 依存元の番号）
- `<機能名>` は英数字・アンダースコア使用（例: `get_file_info`, `sort_links`）
- 分割元の `detailed_design.md` は削除せず残す

### 4.2 分割ファイル先頭のメタ情報

各分割ファイルの先頭に以下のメタ情報テーブルを記載する。

```markdown
## 実装単位メタ情報

| 項目 | 内容 |
|------|------|
| 実装単位番号 | 01 |
| 対象機能 | （機能名） |
| 前提とする実装単位 | なし / 実装単位02が完了していること |
| 推定ステップ数 | 約12ステップ |
```

### 4.2.1 セクション 0「スコープ制約」のコピー

分割元の `detailed_design.md` にセクション 0「スコープ制約（今回やらないこと）」が存在する場合、**全ての分割ファイルにそのセクションをそのままコピーする**こと。

- セクション 0 は実装エージェントへのスコープ制約として機能するため、省略・要約しないこと
- コピー先での位置は実装単位メタ情報テーブルの直後（セクション 1「変更ファイル一覧」の直前）とする

### 4.3 実装単位一覧ファイル（split_index.md）

分割と同時に `docs/cases/<案件名>/split_index.md` を生成する。全実装単位の概要・依存関係・進捗を一覧できるファイル。

```markdown
# 実装単位一覧

**案件名**: <案件名>
**詳細設計書**: detailed_design.md
**分割数**: N 単位
**生成日**: YYYY-MM-DD

| NN | 機能名 | ファイル | 前提単位 | 推定ステップ数 | 実装状況 |
|----|--------|---------|---------|--------------|---------|
| 01 | send_registration_email | detailed_design_01_send_registration_email.md | なし | 約12ステップ | 未着手 |
| 02 | register | detailed_design_02_register.md | 01 | 約8ステップ | 未着手 |

## 依存関係

| 実装単位 | 依存先 | 理由 |
|----------|--------|------|
| 01 send_registration_email | なし | 既存コードのみを参照し、他の新規実装単位に依存しないため |
| 02 register | 01 | `register()` が `send_registration_email()` を呼び出すため |

## 実装対象一覧

| 区分 | 対象 | 実装単位 |
|------|------|----------|
| 関数 | `send_registration_email` | 01 |
| 関数 | `register` | 02 |

## 進捗更新ルール

実装エージェントは各実装単位の完了時に、該当行の実装状況を `未着手` から `実装済み` に更新する。人間はレビュー通過後に `レビュー済み` に更新する。
```

- **実装状況**の初期値は全て `未着手`
- **依存関係**には各実装単位の依存先と、その依存が必要な理由を記載する
- **実装対象一覧**には関数・クラス・モデル・定数・設定値など、実装対象と実装単位の対応を記載する
- 実装エージェントは各実装単位の完了時に該当行を `実装済み` に更新する
- 人間はレビュー通過後に `レビュー済み` に更新する

### 4.4 「前提とする実装単位」の記法ルール

- 前提なし: `なし`
- 前提あり: `実装単位NN が完了していること`（複数の場合はカンマ区切り）
- 実装エージェントは前提単位の実装が完了していることを確認してから着手する

## 5. 分割エージェントへの指示テンプレート

```
docs/cases/<案件名>/detailed_design.md を読み込み、
docs/agent/detailed_design_split_rules.md の分割基準に従って以下の手順で分割ファイルを生成してください。

手順:
1. 全機能を分割基準（関数数・ステップ数・新規ファイル数・依存関係）に従って実装単位に分ける
2. 各実装単位間の呼び出し関係・import 関係を分析し、依存関係を整理する（ファイル出力不要。実装単位数が多い・依存が複雑な場合は、番号確定前に十分時間をかけて依存関係を整理すること）
3. 依存関係のトポロジカル順序に従って NN 番号を付与する（依存先 < 依存元）
   - 循環依存がある場合は、共通定数・例外クラス・インターフェース定義を先行単位として切り出す
4. 各単位を docs/cases/<案件名>/detailed_design_NN_<機能名>.md として出力する
5. 各ファイルの先頭に「実装単位メタ情報」テーブルを付与する（「前提とする実装単位」欄に依存先 NN を明記）
5a. 分割元の detailed_design.md にセクション 0「スコープ制約（今回やらないこと）」が存在する場合、全ての分割ファイルの実装単位メタ情報テーブル直後にそのセクションをそのままコピーする（省略・要約不可）
6. docs/cases/<案件名>/split_index.md を生成する（全実装単位の NN・機能名・ファイル名・前提単位・推定ステップ数を記載し、実装状況は全て「未着手」で初期化する。あわせて「依存関係」「実装対象一覧」「進捗更新ルール」セクションを記載する）

分割元の detailed_design.md は変更しないでください。
```

## 6. 実装エージェントへの指示テンプレート

```
docs/cases/<案件名>/detailed_design_NN_<機能名>.md を読み込み、実装単位メタ情報の
「前提とする実装単位」が完了していることを確認したうえで実装してください。

実装着手前に以下を必ず確認してください。
- セクション 0「スコープ制約（今回やらないこと）」が存在する場合、記載された機能・処理は実装しないこと

実装完了後、以下の2つを行ってください。
1. docs/cases/<案件名>/implementation_review.md にレビュー記録表の雛形を生成する
2. docs/cases/<案件名>/split_index.md の該当行の実装状況を「未着手」→「実装済み」に更新する
```
