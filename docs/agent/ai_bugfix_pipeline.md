## 1. 概要

WEKO3の保守プロセスにおいて、バグ修正工程をAIエージェントと人間の協業で効率化するためのパイプライン設計である。

保守作業では、バックログ（課題管理ツール）に不具合チケットが作成され、不具合の「発生手順」と「事象の説明（エラー内容を含む）」が記載された状態でClaude（エージェント）に渡される。このチケットを起点に、以下までをエージェント主導で行う：

- **バグ調査・原因特定**: エラー内容・不具合発生手順から、ログ・スタックトレース・該当コード・DB状態を突き合わせて根本原因（root cause）を特定する
- **修正方針の立案**: 影響範囲・副作用・最小変更原則の観点で修正方針を立案する（複数案がある場合は比較）。🔴 人間が方針を承認する品質ゲートを設ける
- **修正の実装**: 承認された方針に基づき、最小変更原則で修正コードを実装する

エージェントの主担当を「事象を起点とした原因特定・修正方針立案・修正実装の初期生成」に限定し、原因特定の妥当性判断・修正方針の承認・修正レビュー・回帰確認は人間（およびテストパイプライン）が行う。

なお、チケットには起票者・利用者の個人情報が含まれていることがある。**① チケット受領・事象整理は 🤖 Claude（エージェント）が担当する工程**であり、Claude が生のチケット内容を読み込む最初の工程となる。これを生のまま Claude（外部LLM）へ渡すことはできないため、**パイプラインの最先頭、すなわち ① チケット受領・事象整理よりも前**に、人間側で個人情報をマスキング/一般化する前処理ゲート（⓪ 個人情報マスキング、[6.0](#60--個人情報マスキングclaude投入前の前処理ゲート)）を必ず置く。Claude が受け取るのはマスキング済みデータのみとする。このフェーズは Claude 委譲の対象外とする。

## 2. 前提条件

| 項目 | 内容 |
|------|------|
| 入力はバックログのチケット | 不具合の「発生手順」「事象説明」「エラー内容」「期待動作／実際の動作」が記載されたチケットを起点とする |
| Claude へはマスキング済みデータのみ渡す | チケットに含まれうる個人情報は、Claude が内容を読む最初の工程（① チケット受領・事象整理）よりも前、すなわちパイプラインの最先頭で人間側でマスキング/一般化する。Claude が受け取るのはマスキング済みデータのみとする（[6.0](#60--個人情報マスキングclaude投入前の前処理ゲート)） |
| 設計書の有無で参照資料が変わる | 設計書がある機能の不具合か、設計書外（既存実装）の不具合かによって参照する資料が異なる（[2.1](#21-設計書の有無による参照資料の違い) を参照） |
| 推測で原因を断定しない | 原因はログ・スタックトレース・該当コード・DB状態などの証跡に基づいて特定する。証跡なしの推測で実装を進めない |
| 最小変更原則 | 修正は不具合の根本原因に対する最小の変更にとどめる。便乗リファクタリングや設計書範囲外の変更は行わない |
| 修正方針の人間承認が必須 | 誤った原因のまま実装が進むのを防ぐため、修正方針は 🔴 人間が承認してから実装に着手する |

### 2.1 設計書の有無による参照資料の違い

| 不具合の種別 | 参照資料 | 期待動作の判断基準 |
|-------------|---------|-------------------|
| 設計書がある機能の不具合 | 詳細設計書 / 画面設計書（[../../CLAUDE.md](../../CLAUDE.md)「ドキュメントディレクトリ構成」を参照）+ 該当コード | 設計書に定義された仕様 |
| 設計書外（既存実装）の不具合 | 該当コード + チケットの期待動作 + 機能仕様書（weko-document） | チケットに記載された期待動作・既存の機能仕様書 |

設計書がある場合は「実装が設計書通りか」を判断材料に加える。設計書外の場合は「実装がチケットの期待動作・既存仕様通りか」を判断材料とする。

## 3. 用語集

| 用語 | 説明 |
|------|------|
| Backend Architect | Python/Flask/Invenio3のアーキテクチャ内部動作を理解するエージェント。原因調査の主担当 |
| Code Reviewer | コードの正しさ・保守性・セキュリティ・パフォーマンスに焦点を当てたレビューを行うエージェント。原因分析・修正レビューを担当 |
| Senior Developer | バックエンド実装コードの生成・修正を担当するエージェント |
| Frontend Developer | フロントエンド実装コードの生成・修正、および表示不具合・コンソールエラーの調査を担当するエージェント |
| Security Engineer | セキュリティ起因の不具合（入力検証、認証・認可、情報漏洩等）の場合に脆弱性評価を行うエージェント |
| チケット | バックログに作成された不具合チケット。発生手順・事象説明・エラー内容・期待動作／実際の動作を含む |
| 根本原因（root cause） | 事象を引き起こしている真の原因。表面的なエラーメッセージではなく、その発生源を指す |
| 再現 | チケットの発生手順に従って不具合を実際に発生させること |
| 暫定対応 | 根本原因の解消ではなく、被害の一時的な回避を目的とする対応（ワークアラウンド） |
| 恒久対応 | 根本原因を解消する対応 |
| 回帰確認 | 修正により既存機能を壊していないことの確認 |

## 5. エージェント構成

| フェーズ | 担当 | 入力 | 出力 |
|----------|------|------|------|
| ⓪ 個人情報マスキング | 🔴 人間 / 機関内ローカル・オンプレツール（**Claude委譲対象外**） | 生のチケット内容・添付（個人情報を含みうる） | `docs/tickets/<チケット番号>.md`（新規作成、マスキング済みチケット内容）、再識別対応表（人間側で分離管理） |
| 🔴 品質ゲート⓪ マスキング検証 | 🔴 人間 | マスキング済みデータ | 漏れなしの確認 or 再マスキング指示 |
| ① チケット受領・事象整理 | **Backend Architect** | `docs/tickets/<チケット番号>.md`（発生手順・事象説明・エラー内容） | 構造化された事象情報（再現条件・期待/実際の動作・エラーメッセージ） |
| ② 再現確認 | **Backend Architect** + 🔴 人間 | 構造化された事象情報（マスキング済み）、対象環境 | 再現可否、再現時の証跡 |
| ③ 原因調査・バグ特定 | **Backend Architect** / **Code Reviewer**（FE起因は **Frontend Developer**） | 5種の証跡（7章）、該当コード、設計書（あれば） | 根本原因（root cause）候補、証跡との対応 |
| 🔴 品質ゲート① 原因特定の妥当性 | 🔴 人間 | 原因候補 + 証跡 | 承認 or 再調査指示 |
| ④ 修正方針立案 | **Backend Architect**（セキュリティ起因時は **Security Engineer**） | 確定した原因、該当コード、設計書（あれば） | 修正方針（複数案がある場合は比較） |
| 🔴 品質ゲート② 修正方針承認 | 🔴 人間 | 修正方針 | 承認 or 方針見直し指示 |
| ⑤ 修正実装 | **Senior Developer** (BE) / **Frontend Developer** (FE) | 承認済み修正方針、該当コード | 修正コード |
| ⑥ 人間レビュー＋修正ループ | 🔴 人間 + 🤖（必要時） | 修正コード | 承認 or 修正指示 |
| ⑦ 回帰確認 | 🔴 人間 + テストパイプライン | 修正コード、既存テスト | 回帰確認結果 |

### エージェント選択の理由

- **Backend Architect**: Invenio3/Flaskのアーキテクチャ内部動作の理解があるため、スタックトレース・ログ・該当コードを突き合わせた原因調査と、影響範囲を踏まえた修正方針立案が可能。本パイプラインの調査起点フローの中核を担う
- **Code Reviewer**: 正しさ・保守性・セキュリティ・パフォーマンスに焦点を当てた原因分析が可能。複数の証跡を突き合わせて、フロント側・バックエンド側のどこに原因があるかを切り分けられる。修正レビューも担当
- **Senior Developer**: 確定した修正方針からPEP8準拠の最小変更コードを生成できる（バックエンド修正）
- **Frontend Developer**: 表示不具合・コンソールエラー（JSエラー、CSS、コンポーネント未定義）の調査と、React/AngularJS/jQueryの修正実装が可能（フロントエンド起因の不具合）
- **Security Engineer**: セキュリティ起因の不具合（入力検証不備、認証・認可の欠陥、情報漏洩）の場合にのみ、脆弱性評価と安全な修正方針の提示を担当

> フロントエンド起因の不具合（ブラウザコンソールエラー・表示崩れ・画面遷移不具合）の調査も本パイプラインの対象とする。原因調査は Frontend Developer が開発者コンソールの証跡（7章）を主材料として行う。

> **⓪ 個人情報マスキングは、上記いずれのエージェントにも割り当てない**。マスキングを Claude（外部LLM）に行わせると、その時点で生の個人情報が外部へ渡ってしまい目的と矛盾する（鶏卵問題）。そのため本フェーズは Claude 委譲の対象外とし、🔴 人間または機関内で完結するローカル/オンプレのツールで実施する。パイプライン最先頭（① より前）に置く（詳細は [6.0](#60--個人情報マスキングclaude投入前の前処理ゲート)）。

## 6. 各フェーズの詳細

### 6.0 ⓪ 個人情報マスキング（Claude投入前の前処理ゲート）

チケットには起票者・利用者の個人情報が含まれていることがある。これを生のまま Claude（外部LLM）に読み込ませることはできない。**① チケット受領・事象整理は 🤖 Claude（エージェント）が担当する工程**であり、Claude が生のチケット内容に初めて触れる工程であるため、マスキングは ① よりも前＝**パイプラインの最先頭**に置かなければならない。本フェーズは、Claude が内容を読み込む前に、人間側でチケット内容から個人情報をマスキング/一般化する前処理ゲートである。**① チケット受領・事象整理よりも前に置き、Claude が受け取るのはマスキング済みデータのみ**という不可逆な順序を制度化する。

#### 最重要原則：マスキングは Claude に行わせない（鶏卵問題）

- **マスキングを Claude（外部LLM）自身に行わせてはならない**。Claude にマスキングを行わせると、その時点で生の個人情報が外部に渡ってしまい、「外部LLMに個人情報を渡さない」という目的と矛盾する（鶏卵問題）。
- そのため本フェーズは **Claude 委譲の対象外**とし、**🔴 人間、または機関内で完結するローカル/オンプレのツール**で実施する。
- パイプライン上の位置づけは「**① チケット受領・事象整理よりも前（パイプラインの最先頭）**」に固定する。① 自体が 🤖 Claude 工程であるため、その前にマスキングを完了させることで「Claude が受け取るのはマスキング済みデータのみ」という順序を不可逆に担保する。

#### マスキング対象（2カテゴリに限定）

チケットに実際に記載されうる個人情報はほぼ次の2種に限られるという保守現場の実態に基づき、マスキング対象は以下の **2カテゴリに限定**する。

| 種別 | 例 | 扱い |
|------|-----|------|
| 直接識別子 | 氏名・メールアドレス・電話番号・住所・職員番号/学籍番号・ORCID/研究者ID・ログインID | 仮名化 |
| 環境情報 | 内部ホスト名・IPアドレス・ユーザー名を含むファイルパス（例 `/home/yamada/...`）・URLクエリ中の識別情報 | 一般化 |

> 認証・秘密情報やその他の機微情報がチケットに記載されることは実態としてほぼないが、万一含まれていた場合は同様にマスキング/除去の対象とする。

#### 「壊さない」マスキングの原則

バグはエッジケースで起きるため、マスキングによって不具合の再現条件を壊してはならない。以下を原則とする。

| 原則 | 内容 |
|------|------|
| 構造保持型の仮名化 | 実値は置換するが、フォーマット・構造は保持する（例：メールアドレスは `user_a@example.com` のようにドメイン構造・形式を保つ）。バリデーション系バグの再現に必要 |
| データの「形」の保持 | 文字種・文字数・エンコーディング・特殊文字・絵文字・結合文字・長さ境界など、バグ要因になりうる特性を保存する |
| 一貫性のある仮名化 | 同一人物・同一オブジェクトは常に同じトークンへ一貫してマッピングする（`User_A`, `Host_1` 等）。再現手順の「誰が誰に何をした」という関係性・論理構造を壊さない |

#### 運用・ガバナンス

| 項目 | 内容 |
|------|------|
| 再識別対応表の分離管理 | 仮名↔実値の対応表は人間側で安全に分離管理し、**Claude には絶対に渡さない** |
| 不可逆前提の設計 | マスキングは不可逆である前提で設計する。Claude 側に渡った後は元に戻せない |
| マスキング漏れの二重チェック | マスキング漏れがないことの 🔴 人間レビューを品質ゲート化する（品質ゲート⓪、9章） |
| テキスト以外への注意 | 添付スクリーンショット画像内に映り込む個人情報、ログ/スタックトレース中の実データなど、テキスト以外の見落としやすい箇所にも注意する |

> **品質ゲート⓪（マスキング検証）**: 🔴 人間が、直接識別子・環境情報の2カテゴリにマスキング漏れがないことを二重チェックする。漏れがある場合は再マスキングを行い、合格するまで ①（Claude が内容を読む最初の工程）以降に進まない。

#### 作成場所・手順（プロンプト直接転記ではなくファイル読み込み方式）

本フェーズの成果物は、プロンプトへの直接転記ではなく、**ファイルとして** `docs/tickets/` 配下に格納する。具体的な作業手順は以下の通りである。

| ステップ | 内容 |
|----------|------|
| 1. テンプレートの参照 | 🔴 人間が [docs/conventions/ticket_template.md](../conventions/ticket_template.md) を開く |
| 2. マスキング済みファイルの新規作成 | 🔴 人間が `docs/tickets/<チケット番号>.md`（例: `docs/tickets/BUG-20260705-113.md`。チケット番号にファイル名として使えない文字が含まれる場合はハイフン等に置換）を新規作成し、テンプレートの各項目に**作成する時点でマスキング済みの内容のみ**を記載する |
| 3. 生チケットの非保存 | バックログ（課題管理ツール）からの生の転記や、マスキング前の内容は本リポジトリに一切保存しない。マスキング前後で2ファイル作る運用は取らない |
| 4. 再識別対応表の分離 | 仮名↔実値の再識別対応表はリポジトリ外で人間側が分離管理する（Claude には渡さない） |

> 命名規則の詳細は [../../CLAUDE.new.md](../../CLAUDE.new.md)「ドキュメントディレクトリ構成」の `docs/tickets/` の項も参照。

### 6.1 ① チケット受領・事象整理

本フェーズは 🤖 Claude（Backend Architect）が担当する最初の工程である。前段の ⓪ 個人情報マスキング（[6.0](#60--個人情報マスキングclaude投入前の前処理ゲート)）で人間が作成した **`docs/tickets/<チケット番号>.md` を読み込む**ことを入力とする。プロンプトへの直接転記ではなく、このマスキング済みファイルを読み込ませる方式を前提とする。Backend Architect は、読み込んだ内容から事象を以下の形式に構造化する。後続の再現確認・原因調査を効率化するための前処理である。

| 整理項目 | 内容 |
|----------|------|
| 再現条件 | 不具合を再現するための前提・手順（ログイン状態、対象データ、操作順序） |
| 期待動作 | チケット記載の「本来こうなるべき」動作 |
| 実際の動作 | チケット記載の「実際に起きている」動作 |
| エラーメッセージ | エラー文言・エラーコード・スタックトレースの該当部分（記載があれば） |
| 影響範囲（仮） | 不具合が影響する画面・API・機能の見込み |
| 設計書の有無 | 設計書がある機能か、設計書外かの判定（[2.1](#21-設計書の有無による参照資料の違い)） |

チケットに情報が不足している場合（再現手順が曖昧、期待動作が不明など）は、この時点で不足項目を洗い出し、8章のエスカレーション（追加情報の依頼）に従う。

### 6.2 ② 再現確認

構造化された再現条件に従い、可能な範囲で不具合を再現する。再現は原因調査の前提であり、再現できた状態で証跡（7章）を収集することで、原因特定の精度が上がる。

| ステップ | 担当 | 動作 |
|----------|------|------|
| 1. 再現環境の準備 | 🔴 人間 | 対象環境（Docker等）と再現用データを用意 |
| 2. 発生手順の実行 | 🤖 / 🔴 | チケットの発生手順を実行し、不具合の発生を確認 |
| 3. 再現時の証跡収集 | 🤖 / 🔴 | 再現時点の5種の証跡（7章）を収集 |

#### 再現できない場合の分岐

再現できない場合は、推測で原因調査に進まず、8章のエスカレーションに従う。具体的には以下を切り分ける：

- 環境差異（データ・設定・バージョンの違い）による再現失敗の可能性
- 発生手順・前提条件の記載不足の可能性
- 特定条件下（タイミング・並行処理・特定データ）でのみ発生する可能性

### 6.3 ③ 原因調査・バグ特定

再現できた不具合に対し、5種の証跡（8章）を突き合わせて根本原因（root cause）を特定する。**推測で原因を断定しない**ことを最重要原則とする。

| 調査ステップ | 担当 | 内容 |
|-------------|------|------|
| 1. 証跡の収集 | 🤖 | スタックトレース・コンテナログ・DBログ・DBレコード状況・ブラウザ開発者コンソールを収集（8章） |
| 2. 該当コードの特定 | 🤖 | スタックトレース・ログから不具合発生箇所の該当コードを特定 |
| 3. 期待仕様との突き合わせ | 🤖 | 設計書がある場合は設計書、ない場合はチケットの期待動作・機能仕様書と実際の挙動を突き合わせ |
| 4. 根本原因の提示 | 🤖 | 表面的なエラーではなく、その発生源（root cause）を証跡との対応とともに提示 |

#### 原因調査の出力に含めるもの

- 根本原因（root cause）の候補（証跡と一対一で対応づける）
- 不具合発生箇所の該当コード（ファイルパス・関数名・行）
- 設計書・実装の不整合箇所（設計書がある場合）、または期待動作・実装の不整合箇所（設計書外の場合）
- 各証跡が原因をどう裏付けるかの説明

> **原則**: 「おそらく〜が原因」という証跡なしの推測で原因を断定してはならない。証跡で裏付けられない場合は「未確定」と明示し、9章のエスカレーション（追加調査・追加情報依頼）に進む。

#### フロントエンド起因の場合

表示不具合・コンソールエラー・画面遷移不具合は Frontend Developer が担当し、ブラウザ開発者コンソール（JSエラー・APIリクエスト/レスポンス）を主材料に調査する。バックエンドAPIのレスポンス異常が疑われる場合は、Backend Architect と連携してコンテナログ・APIレスポンスを突き合わせる。

### 6.4 ④ 修正方針立案（品質ゲート）

確定した原因（品質ゲート①を通過したもの）に基づき、修正方針を立案する。修正方針は **🔴 人間が承認してから実装に進む**（品質ゲート②）。これは、誤った原因のまま実装が進むのを防ぐための制度的な歯止めである。

#### 修正方針に含める観点

| 観点 | 内容 |
|------|------|
| 影響範囲 | 修正が及ぶファイル・関数・API・画面、および既存機能への影響 |
| 副作用 | 修正による既存挙動の変化・破壊（breaking change）の有無 |
| 最小変更原則 | 根本原因に対する最小の変更にとどめているか。便乗リファクタリングを含まないか |
| 設計書整合 | 設計書がある場合、修正後のコードが設計書と整合するか（設計書側の修正要否も判断） |
| 暫定/恒久 | 恒久対応か暫定対応か（暫定の場合は恒久対応の方針も併記。9章参照） |

#### 複数案がある場合

複数の修正案が考えられる場合は、各案を以下の観点で比較した上で推奨案を提示する。

| 比較項目 | 案A | 案B |
|----------|-----|-----|
| 影響範囲 | （狭い/広い） | （狭い/広い） |
| 副作用リスク | （低/中/高） | （低/中/高） |
| 変更規模 | （小/中/大） | （小/中/大） |
| 恒久性 | （恒久/暫定） | （恒久/暫定） |

> **品質ゲート②（修正方針承認）**: 🔴 人間が、原因と修正方針の対応・影響範囲・副作用を確認し、承認する。承認されるまで ⑤ 実装に着手しない。方針に問題があれば ③ 原因調査または ④ 修正方針立案に差し戻す。

### 6.5 ⑤ 修正実装

承認済みの修正方針に基づき、修正コードを実装する。担当はバックエンドが Senior Developer、フロントエンドが Frontend Developer。

#### 実装時の必須ルール

1. **最小変更原則**: 承認された修正方針の範囲のみ変更する。便乗リファクタリング・設計書範囲外の変更は行わない
2. **承認方針の厳守**: 品質ゲート②で承認された方針から逸脱しない。実装中に方針の不備が判明した場合は実装を止め、④ に差し戻す
3. **設計書整合**: 設計書がある機能の場合、修正後のコードが設計書と整合することを確認する。設計書側の修正が必要な場合は修正記録（11章）に明記する
4. **規約遵守**: コーディング規約・デザイン規約に従う
5. **既存コードとの整合性**: 既存のimportスタイル・クラス設計パターン・CSS変数を使用する
6. **回帰防止の意識**: 修正対象の周辺で既存機能を壊さないよう、影響範囲（④で特定）に配慮する

エージェントへの入力は**該当箇所のみ**に限定する（付録B）。ファイル全体・プロジェクト全体のコードは渡さない。

### 6.6 ⑥ 人間レビュー＋修正ループ

修正コードに対して人間がレビューを行い、修正指示を出し、必要時にエージェントが修正するループを任意回数繰り返す。

#### レビュー確認項目

| 確認項目 | 内容 |
|----------|------|
| 原因との対応 | 修正が③で特定した根本原因に対応しているか（対症療法になっていないか） |
| 方針との整合 | 品質ゲート②で承認された修正方針通りに実装されているか |
| 最小変更 | 修正が最小変更にとどまっているか。便乗変更が混入していないか |
| 設計書整合 | 設計書がある場合、修正後のコードが設計書と整合しているか |
| 既存コード互換性 | 既存APIのbreaking changeがないか、import循環がないか |
| 回帰リスク | 影響範囲内の既存機能を壊していないか |

#### 指摘の伝え方

実装パイプライン（[ai_implementation_pipeline.md](ai_implementation_pipeline.md) 7.2節）の `implementation_review.md` のような、専用の構造化されたレビュー記録ファイルは本フェーズでは使わない。レビュー指摘はプロンプト上で人間がエージェントに直接伝える方式のままとし、レビュー者名や「🟡指摘」のような構造化ラベル・記号の付与は不要である。普段のセッションでの会話と同じように、シンプルな自然文でそのまま指摘内容を伝えればよい。

例えば、次のように指摘を伝える。

```
このtry-exceptだと想定外の例外まで握りつぶしてしまうので、対象を発生しうる例外に絞ってください。あと、ログにスタックトレースが出ていないので追加してほしいです。
```

エージェントはこれを受けて修正し、修正内容を通常の会話の応答として説明すればよい。修正対応の記録や最終承認についても、専用のファイルやラベルを設けず、プロンプト上のやり取り（人間の指摘とエージェントの応答）で完結させる。

エージェントに修正を依頼する場合、渡す情報は指摘内容・修正対象の関数/コンポーネント・関連する原因調査結果の該当箇所に限定する（付録B）。

### 6.7 ⑦ 回帰確認

修正により既存機能を壊していないことを確認する。修正は局所的でも、影響範囲外の機能に副作用が及ぶことがあるため、回帰確認を必須とする。

| 確認種別 | 方法 | 対象 |
|----------|------|------|
| 既存単体テスト | 修正対象モジュールの既存pytestを実行し、PASSすることを確認 | バックエンド |
| 修正箇所の動作確認 | 修正後にチケットの発生手順を再実行し、不具合が解消されていることを確認 | 両方 |
| 周辺機能の動作確認 | 影響範囲（④で特定）内の周辺機能が従来通り動作することを確認 | 両方 |
| 5種の証跡照合 | 結合動作はテストパイプラインの5種の証跡（[ai_test_pipeline.md](ai_test_pipeline.md) 13章）で照合 | 両方 |

回帰確認の詳細な実行・判定は既存のテストパイプライン（[ai_test_pipeline.md](ai_test_pipeline.md)）に連携する（12章）。バグ再発防止のための回帰テスト追加もここで判断する。

## 7. 原因調査における証跡観点

原因調査（③）では、**推測ではなく証跡に基づいて**根本原因を特定する。テストパイプラインの結合テスト証跡（[ai_test_pipeline.md](ai_test_pipeline.md) 13章）と同じ5種の証跡を、原因調査の材料として使用する。

### 7.1 調査材料とする証跡ソース

| No | 証跡ソース | 調査での確認観点 | 主な収集手段 |
|----|-----------|-----------------|-------------|
| 1 | ブラウザ開発者コンソール | JSエラーの有無、APIリクエスト/レスポンス（ステータスコード・レスポンスボディ）のどこで異常が出ているか | `agent-browser inspect` / ネットワークログ取得 |
| 2 | コンテナログ | アプリケーション（Flask/Invenio）の例外・スタックトレースが出ている箇所 | `docker logs weko-web-1` |
| 3 | DBログ | DB側のエラー・制約違反・スロークエリが出ているか | DBコンテナのログ（`docker logs`）／DBログファイル |
| 4 | DBテーブルのレコード状況 | 不具合発生時のレコード状態（期待と異なるレコード・不整合データ・欠損） | `docker exec` 経由のSQL |
| 5 | スタックトレース | 例外の発生箇所・呼び出し経路（どの関数で・何が起きたか） | コンテナログ／pytestログ／エラー画面 |

> これらに加え、特定したスタックトレース・ログから**該当コード**（ファイルパス・関数・行）を突き合わせ、期待仕様（設計書 or チケットの期待動作）と実際の挙動の差を確認する。

### 7.2 証跡の突き合わせによる原因切り分け

単一の証跡だけで原因を断定しない。複数の証跡を突き合わせて、フロントエンド／バックエンド／DBのどこに根本原因があるかを切り分ける。

| 観測された証跡の組み合わせ | 切り分けの方向 |
|---------------------------|---------------|
| 画面エラー + コンソールにJSエラー、APIは2xx正常 | フロントエンド起因（表示・状態管理） |
| 画面エラー + APIが4xx/5xx + コンテナログに例外 | バックエンド起因（ロジック・例外） |
| API 2xx だが結果が不正 + DBレコードが期待と異なる | バックエンドのロジック or DB状態起因 |
| コンテナログに `SQLAlchemyError` + DBログに制約違反 | DBスキーマ・制約・データ整合性起因 |
| 再現条件によって挙動が変わる | データ依存・タイミング依存（9章のエスカレーションを検討） |

## 8. 再現不可・原因不明時のエスカレーション

再現できない、または原因が特定できない場合は、推測で実装に進まず、以下の分岐手順に従う。

### 8.1 再現不可時の手順

| ステップ | 内容 |
|----------|------|
| 1. 環境差異の確認 | 対象環境のデータ・設定・バージョンがチケット報告環境と一致するか確認 |
| 2. 追加情報の依頼 | チケット起票者に追加情報を依頼（下記項目） |
| 3. 条件依存の検討 | 特定データ・タイミング・並行処理など、特定条件下でのみ発生する可能性を検討 |

#### チケット起票者へ依頼する追加情報の項目

- 不具合発生時の正確な操作手順（クリック順序・入力値）
- 発生環境（ブラウザ種別・バージョン、ログインユーザの権限、対象データのID）
- 発生時刻（コンテナログ・DBログとの突き合わせ用）
- スクリーンショット・ブラウザ開発者コンソールのエラー出力
- 再現頻度（毎回／時々／特定条件下のみ）

### 8.2 原因不明時の手順

証跡を収集しても根本原因が特定できない場合：

| ステップ | 内容 |
|----------|------|
| 1. 未確定の明示 | 「原因未確定」であることを明示し、推測での修正実装に進まない |
| 2. 追加証跡の収集 | ログレベルの引き上げ・追加のDB調査・再現条件の絞り込みなど、追加証跡を収集 |
| 3. 暫定/恒久の切り分け | 影響が大きく即時対応が必要な場合、暫定対応（ワークアラウンド）と恒久対応を切り分ける |
| 4. 人間へのエスカレーション | 🔴 人間に状況（収集した証跡・検討した仮説・未解明点）を共有し、調査方針を判断 |

#### 暫定対応と恒久対応の切り分け

| 区分 | 内容 | 適用条件 |
|------|------|---------|
| 暫定対応（ワークアラウンド） | 根本原因は未解消だが、被害を一時的に回避する対応 | 影響が大きく即時対応が必要だが、根本原因の特定・修正に時間を要する場合 |
| 恒久対応 | 根本原因を解消する対応 | 根本原因が特定でき、最小変更で修正できる場合 |

> 暫定対応を行った場合は、必ず恒久対応のための別チケット（または同チケットへの追記）を残し、根本原因調査を継続する。暫定対応であることを修正記録（11章）に明記する。

## 9. 品質ゲート

| ゲート | 判定者 | 条件 |
|--------|--------|------|
| ⓪ マスキング検証 | 🔴 人間 | チケット内容・添付から直接識別子・環境情報（2カテゴリ）のマスキング漏れがないこと。合格するまで Claude が内容を読む最初の工程（① 以降）に進まない（[6.0](#60--個人情報マスキングclaude投入前の前処理ゲート)） |
| ① 原因特定の妥当性 | 🔴 人間 | 提示された根本原因が証跡と論理的に対応しており、推測でないこと |
| ② 修正方針承認 | 🔴 人間 | 原因に対する修正方針が妥当で、影響範囲・副作用・最小変更原則を満たすこと。承認まで実装に着手しない |
| ③ 修正レビュー | 🔴 人間 | 修正が根本原因に対応し、承認方針通りで、最小変更にとどまり、既存コードとの互換性があること |
| ④ 回帰確認 | 🔴 人間 / テストパイプライン | 既存機能を壊しておらず、不具合が解消され、既存テストがPASSすること |

> **品質ゲート②の重要性**: 本パイプラインは調査起点であるため、**誤った原因のまま実装が進むリスク**が実装パイプラインより高い。修正方針承認（②）を必須の歯止めとし、原因→方針の妥当性を人間が確認してから実装に進む。

## 10. 修正記録（チケットへのフィードバック）

修正完了後、調査・修正の結果をチケットにフィードバックする。再発時の調査や同種不具合の参照に活用するため、以下の雛形項目を記録する。

```markdown
## 修正記録

### 根本原因（root cause）
- （特定した根本原因。表面的なエラーではなく発生源を記述）
- 裏付けた証跡: （スタックトレース／コンテナログ／DBログ／DBレコード／開発者コンソールのうち該当するもの）

### 修正内容
- 変更ファイル: （ファイルパス・関数名）
- 修正方針: （品質ゲート②で承認された方針）
- 修正種別: 恒久対応 / 暫定対応（暫定の場合は恒久対応の予定を記述）

### 影響範囲
- 影響する画面・API・機能: （④で特定した影響範囲）
- 既存挙動への影響（breaking change の有無）: （有/無。有の場合は内容）
- 設計書の修正要否: 要 / 不要（要の場合は対象設計書）

### 回帰確認結果
- 既存単体テスト: PASS / NG
- 不具合解消の確認: （発生手順を再実行した結果）
- 周辺機能の動作確認: （影響範囲内の確認結果）
- 回帰テスト追加: 要 / 不要（要の場合は追加内容。12章参照）
```

修正記録の内容判断（原因・影響範囲・恒久/暫定の妥当性）は人間が最終責任を持つ。エージェントの出力は草案であり、そのまま使用せず必ずレビューする。

## 11. テストパイプライン・関連文書との連携

### 11.1 連携フロー

```
  [バグ修正パイプライン ⑦ 回帰確認]
        │
        ▼  修正コード + 変更ファイル一覧 + 根本原因
  [テストパイプライン]
        │
        ├── 単体テスト（ai_test_pipeline.md 第1部）
        │     → 修正対象モジュールの既存テスト実行
        │     → バグ再発防止のための回帰テスト追加
        │
        └── 結合テスト（ai_test_pipeline.md 第2部）
              → 5種の証跡（13章）で修正後の結合動作を検証
```

修正後の検証は既存のテストパイプライン（[ai_test_pipeline.md](ai_test_pipeline.md)）に連携する。修正パイプラインで収集した根本原因・証跡をテストパイプラインに引き継ぐことで、再発防止に直結したテストを設計できる。

### 11.2 バグ再発防止のための回帰テスト追加

修正した不具合が将来再発しないよう、回帰テストの追加を検討する。

| 不具合種別 | 追加するテスト | 連携先 |
|-----------|--------------|-------|
| ロジックバグ（特定入力で誤動作） | 不具合を再現する入力での単体テスト | 単体テストパイプライン（[ai_test_pipeline.md](ai_test_pipeline.md) 第1部） |
| 例外ハンドリング不備 | 例外発生条件を再現する単体テスト | 単体テストパイプライン |
| 画面・結合動作の不具合 | 発生手順を再現する結合テストシナリオ | 結合テストパイプライン（[ai_test_pipeline.md](ai_test_pipeline.md) 第2部） |

> 回帰テストは「不具合を再現する条件」を起点に設計する。修正前のコードでは失敗し、修正後のコードでは成功するテストを追加することで、再発を機械的に検知できる。

### 11.3 関連文書への参照

| 文書 | 参照する場面 |
|------|-------------|
| [ai_implementation_pipeline.md](ai_implementation_pipeline.md) | 設計書がある機能の修正で、修正に伴い設計書・機能仕様書・マニュアルの更新が必要な場合（実装パイプライン13章・14章のフローを参照） |
| [ai_test_pipeline.md](ai_test_pipeline.md) | 回帰確認・回帰テスト追加・5種の証跡による検証（単体・結合テストパイプライン） |

# 付録

## A. エージェントへの入力限定の原則

実装パイプライン・テストパイプラインと同様に、本パイプラインでもエージェントに渡す情報は**該当箇所のみ**に限定する。ファイル全体・プロジェクト全体のコードは渡さない。

| フェーズ | エージェントに渡す情報（限定） |
|----------|------------------------------|
| ③ 原因調査 | チケットの事象情報、収集した証跡（5種）の該当部分、スタックトレースが指す該当コードの周辺、設計書の該当箇所 |
| ④ 修正方針立案 | 確定した原因、該当コードの該当箇所、設計書の該当箇所、影響範囲の候補 |
| ⑤ 修正実装 | 承認済み修正方針、修正対象の関数/コンポーネント、関連する既存コードの該当箇所（patch path・import位置の確認用） |
| ⑥ 修正ループ | レビューコメントの該当箇所、修正対象の関数/コンポーネント、関連する原因調査結果の該当箇所 |

> ファイル全体やプロジェクト全体を渡すと、トークン消費が増えるだけでなく、調査の焦点がぼやけて誤った原因に誘導されるリスクがある。証跡が指す該当箇所に限定することで、根本原因への集中を保つ。
