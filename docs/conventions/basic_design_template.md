## 5. 非機能要件

### 5.1 パフォーマンス

- 大量データを扱う処理（バッチ・エクスポート等）は非同期処理または進捗表示を設ける
<!-- 案件固有のパフォーマンス要件がある場合はここに追記 -->

### 5.2 セキュリティ

- 認証・認可: Flask-Security + Invenio-Access によるロールベースアクセス制御を使用する。新規 API エンドポイントには `@login_required` デコレータを付与する
- CSRF 対策: Flask-WTF の CSRF トークン検証を使用する
- XSS 対策: Jinja2 テンプレートの自動エスケープを使用する。ユーザー入力を直接 HTML に埋め込まない
- 入力バリデーション: API パラメータは受信時に型チェック・サニタイズを行う
<!-- 案件固有のセキュリティ要件（外部 API 連携・ファイルアップロード等）があれば追記 -->

### 5.3 後方互換性

<!-- コーディング規約に該当記載なし（一般原則として記載） -->
- 既存の公開 API エンドポイント（URL・メソッド・レスポンス形式）は変更しない
- DB マイグレーションはアップ・ダウン両方を実装し、ロールバック可能にする（コーディング規約: モデルクラスを変更する際は Alembic によるマイグレーションツールを自動生成すること）
- 既存の設定値キー（`config.py`・`instance.cfg`）は削除・リネームしない
<!-- 本案件で既存 API や設定を変更する場合は具体的な互換性要件を追記 -->

### 5.4 ログ・エラー通知方針

- ロガー: `current_app.logger` を使用する（`print` 文は使用しない。コーディング規約: print文は納品時（テスト前）には消すこと）
- 外部通知: 原則なし（監視システムへの通知が必要な場合のみ追記）
- ログレベルの使い分け基準（コーディング規約「ログ出力ルール」より）:

| ログレベル | 使用場面 |
|-----------|---------|
| DEBUG | 開発時はどんどん入れてよいが、デバッグに必要になるものを残すこと |
| INFO | ユーザ操作にてデータが追加・変更・削除された場合にその情報を出力（引数・返り値など。ただし個人情報は含めない） |
| WARNING | 通常運用上ありえないことが起きたが、リカバリ可能な場合 |
| ERROR | 通常運用上ありえないことが起き、リカバリ不可能な場合（最低限 Traceback を出力すること） |
| CRITICAL | （コーディング規約に使用基準の記載なし） |

| エラー発生条件 | ログレベル | 外部通知 | 対処方針 |
|-------------|----------|---------|---------|
| DB 接続エラー・予期しない例外 | ERROR | 無 | 処理中断・呼び出し元へエラー返却 |
| レコード未存在（想定内） | WARNING | 無 | デフォルト値返却またはスキップ |
| 【案件固有のエラー条件】 | 【ログレベル】 | 【有 / 無】 | 【対処方針】 |
